# 📘 브라우저 플러그인 관리 및 서버 개발 가이드

## 문서 목적

브라우저 플러그인과 서버가 WebSocket 기반으로 실시간 통신하며 웹페이지 데이터 수집, 모듈 실행, 작업 제어, 로그 기록, 알림 처리를 안정적으로 수행하도록 개발·운영 기준을 제공한다.

## 대상 독자

- 브라우저 플러그인 개발자
- 서버/API 및 모듈 실행 엔진 개발자
- 관리자 UI 개발자
- 보안·운영·DevOps 담당자
- 로그/데이터 관리 담당자

## 범위

- 플러그인 등록, 승인, 인증, 토큰 갱신
- 서버 푸시 기반 모듈 실행 및 플러그인 UI 액션 기반 모듈 실행
- JavaScript, Node.js, Python, Windows 실행 모듈 관리
- 메인 DB와 모듈별 DB 설계
- 작업 종료, 자동 종료, 재시작, 알림, 로그, 권한 관리
- 모듈별 스크린샷·페이지·이미지·동영상 저장 경로 설계
- 관리자 UI 흐름과 메뉴 구조

## 비범위

- Chrome/Edge/Firefox 스토어 배포 심사 절차의 상세 가이드
- 특정 클라우드 벤더 종속 인프라 설계
- VM/Docker 기반 격리 환경 구축 상세 절차
- AI 분석 모델 학습 및 배포 구현 상세
- 실제 운영 DB 마이그레이션 스크립트 전체 세트

## 1. 요구사항 요약

### 1.1 핵심 요구사항

- 플러그인은 서버에 등록 요청을 보내고, 서버 승인 후 JWT 토큰을 발급받아 인증된 상태로 동작한다.
- 서버와 플러그인은 WebSocket 기반 실시간 통신을 기본으로 하며 필요 시 HTTP API를 병행한다.
- 서버는 특정 플러그인에 모듈을 푸시할 수 있고, 플러그인 UI 버튼을 통해 사용자가 직접 서버 액션을 요청할 수 있다.
- 모듈은 `javascript_browser_worker`, `nodejs`, `python`, `windows_exec` 런타임을 구분해 실행한다. 이 4개 문자열이 `modules.runtime` 컬럼과 모든 메시지 payload에서 사용하는 canonical 값이며, 문서 어디에서도 `javascript`, `javascript_server` 같은 동의어·축약형은 사용하지 않는다.
- 모든 실행 결과, 종료 이벤트, 오류, 사용자 액션은 메인 DB와 모듈별 DB에 추적 가능하게 기록한다.
- 모듈별 페이지·이미지·동영상·스크린샷 저장 경로를 관리자 환경 설정에서 지정한다.
- Critical/Warning/Info 우선순위 기반 알림과 외부 메신저 연동을 제공한다.
- RBAC 기반 권한 관리를 적용하고 Windows 실행 모듈은 관리자 승인과 실행 환경 검증을 필수로 한다.

## 2. 프로젝트 개요

### 2.1 목표

본 프로젝트는 브라우저 플러그인과 서버 간 실시간 통신을 통해 웹페이지 데이터를 수집·제어하고, 관리자가 플러그인과 모듈을 안정적으로 운영할 수 있는 시스템을 구축하는 것을 목표로 한다.

기존 단순 푸시 기반 구조를 확장하여 사용자 주도형 액션 구조를 포함한다. 즉, 사용자가 플러그인 UI 버튼을 눌러 서버에 데이터를 전송하거나 특정 모듈을 실행할 수 있다.

### 2.2 핵심 기능

- 플러그인 등록 및 승인 절차
- 서버와 플러그인 간 WebSocket 실시간 통신
- 서버 푸시 기반 모듈 실행
- 사용자 UI 액션 기반 모듈 실행
- 플러그인 UI 버튼: “페이지 전송”, “스크린샷 전송”, “A프로젝트 실행”, “B프로젝트 실행”
- JavaScript, Node.js, Python, Windows 내부 프로그램 실행 지원
- 작업 종료 및 알림 시스템
- 무한 루프 방지 및 강제 종료
- 모듈별 실행 결과 및 기록 관리
- 모듈별 저장 디렉토리 환경 설정

### 필수 요구사항

- 플러그인 등록, 인증, 액션, 실행, 종료, 결과 기록의 전체 흐름을 추적 가능하게 구현한다.
- 모듈별 저장 경로는 관리자 설정을 통해 관리되어야 한다.

### 권장 사항

- 플러그인 UI 액션은 서버 모듈 정의와 매핑 테이블로 관리한다.
- 실행 결과와 알림은 동일한 상관관계 ID(correlation ID)로 연결한다.

### 향후 아이디어

- 사용자 액션 로그를 분석해 자주 사용하는 작업을 자동 추천한다.

## 3. 시스템 주요 특징

### 3.1 사용자 주도형 액션 구조

플러그인 UI는 기본 메뉴로 “페이지 전송”, “스크린샷 전송”, “A프로젝트 실행”, “B프로젝트 실행”을 제공한다. 사용자가 버튼을 누르면 플러그인은 서버에 `action` 메시지를 전송하고, 서버는 해당 액션에 연결된 모듈을 실행한다.

#### 기본 액션 코드 매핑

버튼 라벨(한글 UI 표시)과 실제로 메시지에 담기는 `action` 문자열 값, 연결 모듈은 아래처럼 고정한다. 새 버튼을 추가할 때도 이 표에 먼저 행을 추가한 뒤 구현한다.

| 버튼 라벨 | `action` 값 | 연결 모듈(`modules.name`) | 기본 runtime |
| --- | --- | --- | --- |
| 페이지 전송 | `send_page` | `page_capture` | `javascript_browser_worker` |
| 스크린샷 전송 | `send_screenshot` | `screenshot_capture` | `javascript_browser_worker` |
| A프로젝트 실행 | `run_project_a` | `project_a` | 모듈 정의에 따름 |
| B프로젝트 실행 | `run_project_b` | `project_b` | 모듈 정의에 따름 |

```json
{
  "type": "action",
  "plugin_id": "uuid-1234",
  "action": "run_project_a",
  "payload": { "screenshot": "base64-data", "idempotency_key": "uuid-5678" }
}
```

### 3.2 멀티 런타임 모듈 관리

모듈 정의에는 `runtime` 필드를 포함한다.

- `javascript_browser_worker`: 브라우저 확장 내부 Web Worker 실행
- `nodejs`: 서버 Node.js 프로세스/워커 실행 (과거 `javascript_server`라는 이름을 병용했으나, 혼선을 막기 위해 `nodejs`로 단일화한다. 기존 코드·설정에 `javascript_server`가 남아 있다면 마이그레이션 시 `nodejs`로 치환한다.)
- `python`: 서버 Python 워커 또는 작업 큐 실행
- `windows_exec`: 서버가 설치된 Windows 호스트에서 승인된 실행 파일만 실행

`push_module`은 브라우저에서 실행 가능한 모듈(`javascript_browser_worker`)만 전달한다. `nodejs`, `python`, `windows_exec` 같은 서버 런타임 모듈은 플러그인에 코드를 내려보내지 않고, 서버 측 실행 엔진에서 실행한 뒤 결과와 상태만 플러그인 또는 관리자 UI에 전달한다.

#### 실행 주체 매트릭스

| 런타임 | 실행 주체 | 입력 데이터 | 출력 데이터 | 권한 | 제한 시간 | 종료 방식 | 로그 위치 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `javascript_browser_worker` | 브라우저 확장 내부 Web Worker | 서버가 `push_module`로 전달한 브라우저 실행 가능 스크립트, 현재 페이지에서 허용된 DOM 스냅샷/URL/스크린샷, 사용자 액션 payload | `result` 메시지 payload, 수집 HTML/텍스트/이미지 메타데이터, 오류 정보 | 확장 manifest 권한과 사용자 승인 범위 내 권한만 사용하며 DOM·쿠키·세션 접근은 최소화 | 모듈 정책의 브라우저 실행 타임아웃과 Web Worker watchdog 기준 | 서버 `terminate` 메시지, Worker `terminate()`, 타임아웃 또는 브라우저 확장 언로드 | 브라우저 확장 로컬 로그, 서버 수신 `result`, 메인 DB `system_logs`, 모듈 DB `execution_logs` |
| `nodejs` | 서버의 Node.js 프로세스 또는 워커 | 플러그인 `action`/`result` payload, 서버 DB 조회 결과, 환경 설정, 작업 큐 메시지 | 모듈 실행 결과, 파일 저장 경로, 후속 WebSocket/HTTP 응답, 오류 정보 | 서버 런타임 서비스 계정 권한과 모듈별 RBAC 정책으로 제한 | 모듈 정책의 서버 실행 타임아웃, 작업 큐 visibility timeout, 리소스 watchdog 기준 | 프로세스/워커 취소 신호, 작업 큐 취소, 타임아웃 시 강제 종료 및 필요 시 재시작 | 서버 애플리케이션 로그, 메인 DB `system_logs`/`module_records`, 모듈 DB `execution_logs` |
| `python` | 서버의 Python 워커 또는 작업 큐 | 플러그인 수집 데이터, 모듈 파라미터, DB/파일 입력, 작업 큐 메시지 | 분석·변환 결과, 생성 파일 경로, 표준 출력/오류 요약, 오류 정보 | Python 워커 서비스 계정 권한과 모듈별 RBAC 정책으로 제한 | 모듈 정책의 Python 작업 타임아웃, 작업 큐 visibility timeout, CPU/메모리 제한 기준 | 작업 취소 신호, 큐 작업 중단, 타임아웃 시 워커 프로세스 종료 | Python 워커 로그, 서버 집계 로그, 메인 DB `module_records`, 모듈 DB `execution_logs` |
| `windows_exec` | 서버가 설치된 Windows 호스트의 승인된 실행 파일 | 승인된 실행 파일 경로, 서명 검증 결과, 허용된 인자, 작업 입력 파일/환경 변수 | 종료 코드, 표준 출력/오류 요약, 생성 파일 경로, 실행 감사 결과 | `super-admin` 승인, 코드 서명 검증, 허용 목록, Windows 서비스 계정 권한으로 제한 | 모듈 정책의 OS 실행 타임아웃, 프로세스 watchdog, CPU/메모리 제한 기준 | 관리자 강제 종료, watchdog kill, 타임아웃 종료, 호스트 서비스 재시작 | Windows 이벤트 로그, 서버 실행 로그, 메인 DB `system_logs`/`module_records`, 모듈 DB `execution_logs` |

VM/Docker 기반 격리 환경은 비범위로 두되, 리소스 사용량 실시간 모니터링과 실행 전 검증으로 안정성을 확보한다.

### 3.3 보안 및 권한 관리

- RBAC(Role-Based Access Control) 기반 권한 세분화
- OS 프로그램 실행 시 관리자 승인 필수
- 실행 전 코드 서명 검증 **또는** SHA-256 해시 allowlist 검증
- 샌드박스 테스트 자동화
- Windows 실행 모듈의 추가 실행 환경 검증

#### 코드 서명 검증 vs 해시 allowlist

Authenticode 코드 서명은 배포용 상용 실행 파일에는 적합하지만, 운영자가 직접 작성·컴파일한 `.exe`/`.bat`/PyInstaller 산출물은 유효한 서명서를 갖지 않는 경우가 많다. 코드 서명 검증만 필수로 강제하면 정작 운영자 본인이 만든 실행 파일이 차단될 수 있으므로, 다음 두 방식을 모두 지원하고 모듈별로 선택하게 한다.

- **코드 서명 검증**: 배포된 서드파티 실행 파일, 신뢰할 수 있는 게시자 인증서가 있는 경우.
- **SHA-256 해시 allowlist**: 운영자가 실행 파일의 SHA-256 해시를 직접 등록하고, 실행 전 서버가 대상 파일 해시를 계산해 등록된 해시와 일치할 때만 허용한다. 파일이 변경되면(재컴파일 등) 해시가 달라지므로 관리자가 다시 승인해야 한다.
- 두 방식 모두 `windows_exec_allowlist` 테이블(부록 E 참조)에 등록 이력과 승인자·승인 시각을 기록한다.

#### 개인 단독 운영 시 권한 모델 간소화

본 문서의 RBAC 4단계(`super-admin/operator/auditor/developer`)와 6.1의 토큰 회전·재사용 탈취 감지는 다수 사용자·다수 기기 운영을 전제로 한 설계다. 단일 운영자가 로컬 1대에서만 사용하는 경우, 아래처럼 축소해도 핵심 안전장치는 유지된다.

- 역할 구분 없이 단일 관리자 계정만 두되, `windows_exec` 실행 승인 절차(관리자 승인 + 서명/해시 검증)는 그대로 유지한다.
- refresh token 회전·재사용 탈취 감지 로직은 생략하고, 장기 access token 1개를 발급하되 만료·폐기(revoke)만 지원해도 된다.
- 다만 §6.1의 `plugin_id + token` 검증과 §6.4의 Origin 검증·loopback 바인딩은 로컬 단독 운영이어도 생략하지 않는다. 브라우저에서 방문하는 임의의 웹페이지가 로컬 WebSocket 서버에 연결을 시도할 수 있기 때문이다.

### 3.4 브라우저 확장 구조

Chrome과 Microsoft Edge 확장은 **Manifest V3**를 기준으로 개발한다. Manifest V2는 신규 배포와 장기 유지보수 대상에서 제외하며, 백그라운드 처리는 지속 실행 background page가 아니라 Manifest V3의 extension service worker에서 수행한다.

#### 기본 파일 구조

```text
extension/
├── manifest.json              # Manifest V3 확장 메타데이터, 권한, 진입점 정의
├── background/
│   └── service-worker.js      # 서버 WebSocket 연결, 명령 라우팅, 탭/스크립트 제어
├── popup/
│   ├── popup.html             # 사용자 액션 버튼 UI
│   ├── popup.css
│   └── popup.js               # 페이지 전송, 스크린샷 전송, 프로젝트 실행 요청
├── content/
│   └── content-script.js      # 현재 페이지 DOM/텍스트 수집 및 페이지 컨텍스트 상호작용
├── options/
│   ├── options.html           # 서버 URL, 플러그인 ID, 사용자 설정 화면
│   └── options.js             # 설정 저장/검증
└── assets/                    # 아이콘, 정적 리소스
```

- `manifest.json`은 `manifest_version: 3`을 명시하고 `background.service_worker`, `action.default_popup`, `options_page`, `content_scripts` 또는 동적 주입 대상을 선언한다.
- background service worker는 WebSocket 세션 관리, 서버 명령 처리, `chrome.scripting` 호출, 토큰 갱신 요청, 재연결 백오프를 담당한다.
- popup UI는 사용자가 명시적으로 시작한 액션만 background로 전달하며, 장시간 작업이나 네트워크 연결을 직접 보유하지 않는다.
- content script는 현재 탭의 DOM 접근과 최소한의 페이지 데이터 수집만 담당하고, 서버 통신과 토큰 처리는 background로 위임한다.
- options page는 서버 주소, 등록 상태, 디버그 로그 수준 등 사용자 또는 운영자가 변경 가능한 설정을 `chrome.storage`에 저장한다.

#### 최소 권한 원칙

| 권한 | 사용 목적 | 적용 기준 |
| --- | --- | --- |
| `activeTab` | 사용자가 popup 버튼을 누른 현재 탭에 한해 일시적으로 스크립트 실행 또는 데이터 수집 | 기본 권한으로 사용하며 광범위한 host 권한보다 우선한다. |
| `scripting` | Manifest V3에서 content script를 동적으로 주입하거나 함수 실행 | 사용자 액션 또는 서버가 승인된 작업을 요청한 경우에만 호출한다. |
| `storage` | 플러그인 등록 정보, JWT/갱신 토큰 참조, 서버 URL, 사용자 설정 저장 | 민감 정보는 만료 시간을 포함하고 필요 시 암호화 또는 OS/브라우저 보안 저장소 연계를 검토한다. |
| host permissions | 특정 도메인에서 자동 수집 또는 상시 content script 실행이 필요한 경우 | `https://*/*` 같은 전역 권한은 금지하고, 운영에 필요한 도메인 패턴만 allowlist로 선언한다. |

선택 권한은 기능이 활성화될 때만 요청하고, 권한 요청 사유를 popup 또는 options page에서 사용자에게 명확히 표시한다. 쿠키, 다운로드, 히스토리, 탭 전체 접근 같은 추가 권한은 본 문서의 기본 범위에 포함하지 않으며 별도 보안 검토와 관리자 승인을 거쳐야 한다.

#### 페이지 HTML 및 스크린샷 수집 API

- 페이지 HTML/텍스트 수집은 content script에서 `document.documentElement.outerHTML`, `document.body.innerText`, `document.URL`, `document.title`, 필요한 meta 태그를 읽어 구조화 payload로 만든다.
- 페이지 컨텍스트에서만 접근 가능한 값이 필요하면 `chrome.scripting.executeScript`로 현재 활성 탭에 제한적으로 함수를 주입하고, 결과만 background에 반환한다.
- 스크린샷 수집은 background service worker에서 `chrome.tabs.captureVisibleTab`을 사용해 현재 창의 보이는 영역만 캡처한다. 전체 페이지 스크린샷이 필요하면 content script가 스크롤 위치와 viewport 정보를 제공하고 background가 구간별 `captureVisibleTab` 결과를 합성하되, 사용자 명시 액션과 도메인 allowlist를 전제로 한다.
- 수집 payload에는 `url`, `captured_at`, `tab_id`, `frame_id`, `content_hash`, `mime_type`, `byte_size`, `correlation_id`를 포함해 서버 저장 경로와 실행 로그를 추적할 수 있게 한다.

#### 메시지 흐름 분리

content script와 background 간 메시지는 브라우저 내부 데이터 수집·제어 흐름으로 제한하고, 서버 WebSocket 메시지는 background와 서버 간 인증된 제어 흐름으로 분리한다.

```text
[popup UI]
  └─ chrome.runtime.sendMessage(action 요청)
      → [background service worker]
          ├─ chrome.scripting.executeScript / chrome.tabs.captureVisibleTab
          └─ chrome.tabs.sendMessage(현재 탭 수집 요청)
                → [content script]
                    └─ DOM/텍스트/메타데이터 응답
```

```text
[background service worker]
  ├─ WebSocket 연결 수립: wss://server/ws/plugins?plugin_id=...
  ├─ Authorization/JWT 또는 등록 토큰 검증
  ├─ heartbeat/ping-pong 및 지수 백오프 재연결
  ├─ 서버 push_module/terminate/config_update 수신
  └─ action/result/error/log 메시지 송신
      → [서버 WebSocket Gateway]
          └─ 인증, 권한 검증, 모듈 실행 엔진/DB 기록 연계
```

- content script는 서버 주소, JWT, WebSocket 객체를 직접 보유하지 않는다.
- background는 content script 응답을 검증·정규화한 뒤 서버 메시지 스키마에 맞춰 전송한다.
- 서버에서 내려온 명령은 background에서 권한, 대상 탭, 사용자 승인 필요 여부를 확인한 뒤 content script 또는 popup 상태로 라우팅한다.
- 모든 내부 메시지와 WebSocket 메시지는 동일한 `correlation_id`를 공유해 UI 이벤트, 수집 데이터, 서버 실행 결과를 연결한다.

#### Firefox WebExtensions 호환성 검토 표

Firefox 지원이 필요한 경우 Chrome/Edge 구현을 그대로 전제하지 말고 아래 차이를 별도 호환성 계층에서 처리한다.

| 항목 | Chrome/Edge Manifest V3 기준 | Firefox WebExtensions 검토 사항 | 대응 방안 |
| --- | --- | --- | --- |
| background 실행 모델 | Manifest V3 extension service worker | Firefox의 Manifest V3 지원 범위와 service worker 동작 제약을 버전별로 확인해야 한다. | `browser.*` Promise API 래퍼와 background 초기화/재연결 로직을 분리한다. |
| API 네임스페이스 | `chrome.*` 콜백/Promise 혼재 | Firefox는 `browser.*` Promise API가 기본이다. | 공통 adapter에서 `chrome`/`browser` 차이를 흡수한다. |
| 스크립트 주입 | `chrome.scripting` | 일부 버전·권한 조합에서 동작 차이가 있을 수 있다. | 정적 content script와 동적 주입 경로를 모두 테스트한다. |
| 스크린샷 | `chrome.tabs.captureVisibleTab` | 권한 요구와 반환 형식은 유사하나 브라우저별 제한이 다를 수 있다. | 브라우저별 캡처 한도, 이미지 포맷, 오류 코드를 표준화한다. |
| host permissions | Manifest V3 `host_permissions` | 매니페스트 키와 사용자 권한 UX 차이를 확인해야 한다. | 도메인 allowlist 설정을 브라우저별 manifest 생성 단계에서 분기한다. |

Firefox는 초기 필수 지원 대상이 아니라 선택 지원 대상으로 두며, 지원이 확정되면 브라우저별 E2E 테스트와 스토어 정책 검토를 완료한 뒤 릴리스한다.

### 필수 요구사항

- 모든 명령 및 데이터 전송은 `plugin_id + token` 검증을 거쳐야 한다.
- `windows_exec` 모듈은 super-admin 권한과 사전 승인 없이는 실행할 수 없다.

### 권장 사항

- 런타임별 실행 정책과 제한값을 별도 설정 파일이나 DB 테이블로 관리한다.
- 위험도 높은 모듈은 배포 전 자동 테스트와 수동 승인 단계를 모두 거친다.

### 향후 아이디어

- 런타임별 위험 점수를 계산해 승인 워크플로를 자동 조정한다.

## 4. 데이터베이스 설계

### 4.1 메인 데이터베이스 `main.db`

`main.db`는 중앙 관리 데이터베이스이며 플러그인 등록, 토큰 관리, 모듈 정의, 시스템 로그, 모듈 실행 참조 기록을 관리한다. 아래 표가 `main.db`에 존재해야 하는 테이블의 전체 목록이며, 각 테이블의 전체 컬럼 정의(DDL)는 부록 E를 따른다.

| 테이블 | 역할 |
| --- | --- |
| `browser_plugins` | 플러그인 등록 및 상태 관리 |
| `tokens` | JWT 토큰 및 만료일 관리 |
| `modules` | 모듈 정의, 설명, 버전, 스크립트, 런타임 관리 |
| `system_logs` | 관리자 이벤트 및 시스템 이벤트 기록 |
| `module_records` | 모듈 실행 참조 기록과 결과 DB 경로 관리 |
| `module_settings` | 모듈별 저장 경로(page/image/video) 환경 설정 (DDL은 부록 B.1) |
| `alert_logs` | Critical/Warning/Info 알림 발생·확인(acknowledged) 이력 (§7.3 알림 공통 필드 기준) |
| `windows_exec_allowlist` | `windows_exec` 모듈의 승인된 실행 파일 목록과 서명/해시 검증 이력 (§3.3) |

> 이전 버전에서는 `alert_logs`, `module_settings`가 본문 예시 코드(§9.1, 부록 B)에서만 등장하고 이 표에는 빠져 있었다. 구현 체크리스트(부록 A.2)도 동일하게 갱신했다.

### 4.2 모듈 전용 데이터베이스 `module_{id}.db`

모듈 전용 DB 생성 단위는 **모듈별 1개**를 기본 정책으로 선택한다. 즉, 하나의 모듈은 하나의 SQLite 파일 `module_{id}.db`를 가지며, 각 실행은 DB 내부의 `run_id`로 구분한다. `모듈 실행별 1개` DB 파일 생성은 파일 수 폭증과 운영 복잡도 증가를 유발하므로 금지하고, `기간별 파티션`은 SQLite 파일 생성 단위가 아니라 PostgreSQL·TimescaleDB·ClickHouse 등 대규모 운영 대안에서만 검토한다.

| 테이블 | 역할 |
| --- | --- |
| `collected_data` | URL, 콘텐츠 타입, 저장 경로, 크기, 해시 등 수집 데이터 메타데이터 저장 |
| `execution_logs` | 시작/종료, 에러 로그, 실행 환경 기록 |
| `artifact_paths` | HTML, 스크린샷, 이미지, 동영상 등 대형 산출물의 파일 또는 object storage 경로 기록 |
| `screenshot_paths` | 환경 설정에서 지정된 스크린샷 저장 경로 기록 |

#### DB 생성·보관·백업 정책

- DB 생성 단위는 모듈별 1개(`module_{id}.db`)로 고정하고, 신규 모듈 등록 시 최초 실행 전 빈 DB와 스키마를 생성한다.
- SQLite 모듈 DB 파일 수 상한은 활성 모듈 기준 1,000개로 제한한다. 상한의 80%에 도달하면 관리자 UI와 알림 채널에 경고를 표시하고, 상한 초과 전 신규 모듈 등록 제한 또는 대규모 운영 대안 전환을 검토한다.
- 활성 데이터 보관 기간은 기본 180일로 하고, 180일이 지난 실행 데이터는 월 단위 아카이브 묶음으로 이동한다. 법무·감사 요구가 있는 경우 `main.db.module_records.retention_until`에 보관 만료일을 명시한다.
- 아카이브 압축 방식은 `tar.zstd`(`.tar.zst`)를 기본으로 사용하고, 장기 보관 또는 호환성이 중요한 환경에서는 `tar.gz`를 허용한다. 아카이브에는 모듈 DB 스냅샷, 산출물 메타데이터 manifest, SHA-256 checksum 목록을 포함한다.
- 백업은 증분 백업을 매일 1회, 전체 백업을 매주 1회 수행한다. 백업 완료 후 샘플 복구 검증과 checksum 검사를 수행하고 결과를 `system_logs`에 기록한다.
- 복구 절차는 ① 대상 `module_id`와 `run_id` 범위 확인, ② `main.db.module_records`의 `archived_at`·아카이브 위치 조회, ③ 아카이브 checksum 검증, ④ 격리된 임시 경로에 압축 해제, ⑤ 모듈 DB 무결성 검사와 산출물 해시 검증, ⑥ 운영 경로로 원자적 교체 또는 읽기 전용 임시 마운트, ⑦ 관리자 UI에서 복구 완료 상태와 감사 로그 확인 순서로 수행한다.
- 아카이빙 후 조회는 `main.db.module_records`의 메타데이터를 우선 검색하고, 상세 조회 요청 시 아카이브 manifest를 읽어 미리보기 가능한 항목만 스트리밍하거나 관리자가 승인한 경우에만 임시 복원한다.
- 스크린샷, 원본 HTML, 이미지, 동영상 같은 대형 payload는 DB BLOB으로 저장하지 않는다. 파일 시스템 또는 object storage에 저장하고 DB에는 `artifact_type`, `storage_uri`, `content_hash`, `byte_size`, `mime_type`, `created_at`, `retention_until` 같은 메타데이터와 경로·해시만 저장한다.

#### 동시 쓰기 많은 환경의 대안

- SQLite 쓰기 락 경합이 빈번하거나 동시 쓰기 작업자가 많은 환경에서는 모듈별 SQLite를 고정 전제로 삼지 않는다.
- 트랜잭션 무결성과 범용 쿼리가 중요하면 PostgreSQL을 사용하고, 시계열 실행 로그·메트릭 중심이면 TimescaleDB hypertable을 사용한다.
- 대량 이벤트 분석, append-only 로그, 집계 쿼리가 중심이면 ClickHouse를 사용한다.
- 스크린샷·HTML·동영상 등 대형 payload가 많은 경우 object storage에 원본을 저장하고 PostgreSQL 등 메타데이터 DB로 경로, 해시, 보존 정책, 접근 권한만 관리한다.

### 4.3 DB 최적화 전략

- DB 생성 단위는 모듈별 1개로 유지하고, 모듈 실행별 DB 파일 생성은 금지한다.
- `main.db.module_records`는 별도 모듈 DB와 산출물의 중앙 참조 테이블로 사용하며 최소 필드로 `module_id`, `run_id`, `module_db_path`, `artifact_base_path`, `checksum`, `archived_at`, `retention_until`을 둔다.
- SQLite 파일이 `main.db`와 `module_{id}.db`처럼 분리될 경우 파일 간 직접 외래키 보장을 전제로 설계하지 않는다. `main.db.module_records.run_id`와 각 `module_{id}.db` 내부 실행·수집 테이블의 `run_id`를 논리적 연결 키로 사용한다.
- `module_{id}.db` 내부에는 `run_id` 기준 인덱스를 생성해 특정 실행 결과, 수집 데이터, 로그를 빠르게 조회하도록 한다.
- 분리된 DB 파일 간 무결성은 DB 엔진의 외래키에 의존하지 않고, 주기적으로 실행되는 consistency checker 작업이 `module_records`의 `module_db_path`, `artifact_base_path`, `checksum`, `archived_at`과 모듈 DB 내부 `run_id` 존재 여부를 검증한다.
- 실행 환경별 성능과 오류 패턴 분석을 위해 `runtime` 필드를 로그에 포함한다.
- 대규모 운영에서는 모듈별 DB 다중 파일 구조만 고정 전제로 삼지 말고 단일 DB 파티셔닝, PostgreSQL 스키마 분리, TimescaleDB, ClickHouse, 오브젝트 스토리지 + 메타데이터 DB 구조를 함께 비교한다.
- 대규모 확장 시 ELK Stack 또는 유사 로그 분석 시스템과 실시간 스트리밍 처리를 연동한다.

#### 대규모 운영 대안 비교

| 대안 | 장점 | 주의점 | 적합한 상황 |
| --- | --- | --- | --- |
| 모듈별 SQLite 다중 파일 | 모듈 단위 격리와 백업·아카이빙이 단순함 | 파일 수 증가, 교차 조회 비용, 파일 간 외래키 부재를 consistency checker로 보완해야 함 | 중소규모 운영, 모듈별 데이터 수명주기가 명확한 경우 |
| 단일 DB 파티셔닝 | 중앙 쿼리와 트랜잭션 관리가 쉬우며 운영 도구가 단순함 | 파티션 설계와 인덱스 관리가 필요하고 단일 DB 장애 영향이 커질 수 있음 | `run_id`·`created_at` 기준 조회가 많고 하나의 DB 엔진으로 운영하려는 경우 |
| PostgreSQL 스키마 분리 | 스키마별 격리와 중앙 관리, 강한 제약 조건, 고급 인덱스 활용 가능 | PostgreSQL 운영 역량과 마이그레이션 설계가 필요함 | 데이터 규모가 커지고 교차 분석·권한 분리가 중요한 경우 |
| TimescaleDB | 시간 기준 파티셔닝과 보존 정책, 압축, 시계열 집계가 강력함 | PostgreSQL 확장 운영과 hypertable 설계가 필요함 | 실행 로그·메트릭처럼 시간 범위 조회와 자동 보존 정책이 중요한 경우 |
| ClickHouse | append-only 대량 로그와 분석 집계 쿼리 성능이 우수함 | UPDATE/DELETE 중심 트랜잭션에는 부적합하며 별도 운영 역량이 필요함 | 대량 이벤트 분석, 장기 로그 분석, 대시보드 집계가 핵심인 경우 |
| 오브젝트 스토리지 + 메타데이터 DB | 대용량 파일·스크린샷·동영상 저장 비용과 확장성이 우수함 | 메타데이터와 객체 무결성 검증, 수명주기 정책, 재처리 전략이 필요함 | 바이너리 산출물이 많고 장기 보관·저비용 확장이 필요한 경우 |

### 필수 요구사항

- 메인 DB에는 중앙 관리 참조 기록을 남기고, 모듈 DB에는 실제 실행 결과 메타데이터를 저장한다.
- `main.db.module_records`는 아래 필드를 모두 포함하는 하나의 테이블이다(이전 버전에서 두 문장으로 나뉘어 있던 필드 목록을 통합함): `plugin_id`, `module_id`, `run_id`, `runtime`, `correlation_id`, 시작/종료 시간, 종료 상태, `module_db_path`, `artifact_base_path`, `checksum`, `archived_at`, `retention_until`. 전체 DDL은 부록 E를 따른다.
- 별도 SQLite 파일 간 직접 외래키 보장을 전제로 구현하지 않고, `module_records.run_id`와 `module_{id}.db` 내부 `run_id`를 논리적으로 연결한다.
- 무결성 검증은 주기적 consistency checker 작업으로 수행한다.

### 권장 사항

- 모듈별 DB는 보존 기간, 용량, 파일 수 상한을 모두 고려해 아카이빙한다.
- 자주 조회되는 `plugin_id`, `module_id`, `created_at`, `status`와 모듈 DB 내부 `run_id`에는 인덱스를 둔다.
- 대규모 운영 전환 시 모듈별 DB 다중 파일, 단일 DB 파티셔닝, PostgreSQL 스키마 분리, TimescaleDB, ClickHouse, 오브젝트 스토리지 + 메타데이터 DB의 운영 비용과 장애 복구 방식을 비교한다.

### 향후 아이디어

- 실행 로그를 이벤트 스트림으로 발행해 대시보드와 알림 시스템이 실시간으로 구독하도록 구성한다.

## 5. 메시지 및 실행 흐름

### 5.1 메시지 타입

WebSocket 공개 메시지 타입은 플러그인과 서버 사이에서 실제로 교환되는 계약만 포함한다. `push_module`은 서버가 브라우저 실행 가능 모듈을 특정 플러그인에 배포하는 메시지이고, `action`은 플러그인 UI에서 사용자가 발생시킨 요청을 서버에 전달하는 메시지이다. 기존 `execute`는 의미가 서버 직접 명령, 내부 작업 명령, 플러그인 명령 사이에서 중복되므로 공개 WebSocket 메시지 타입에서 제거한다. 관리자 즉시 명령과 서버 내부 작업은 `push_module`으로 플러그인에 배포하거나 서버 내부 job 모델(`job_type`, `job_id`, `target_runtime`, `requested_by`, `status`)로 처리하고, 플러그인에는 상태 변경이나 결과만 메시지로 전달한다.

| 방향 | 타입 | 정의 | 필요한 권한 | 요청/응답 쌍 | 실패 처리 |
| --- | --- | --- | --- | --- | --- |
| 플러그인 → 서버 | `register` | 신규 플러그인이 서버에 등록과 승인 대기를 요청한다. | 플러그인 설치 인스턴스의 등록 키 또는 최초 등록 nonce. | 요청: `register` / 응답: `approval` | 등록 키 불일치, 중복 등록, 정책 위반 시 `approval.status: denied`와 오류 코드를 반환하고 감사 로그를 기록한다. |
| 서버 → 플러그인 | `approval` | 등록 승인 여부와 인증 토큰 또는 거절 사유를 전달한다. | 서버 등록 승인 서비스 권한, 필요 시 관리자 승인 권한. | 요청: `register` / 응답: `approval` | 토큰 발급 실패 또는 승인 거절 시 `status: failed` 또는 `denied`, `retryable` 값을 명시하고 재등록 가능 조건을 안내한다. |
| 서버 → 플러그인 | `push_module` | 서버가 `javascript_browser_worker` 런타임으로 실행 가능한 모듈을 특정 플러그인에 배포한다. 서버 런타임 코드(`nodejs`, `python`, `windows_exec`)는 포함하지 않는다. | 모듈 배포 권한을 가진 `operator` 이상, 모듈 승인 상태, 대상 플러그인 권한, 유효한 서버 서명. | 요청: `push_module` / 응답: 플러그인의 수락·실행 결과 `result` | 인증·권한·서명·런타임 검증 실패 시 플러그인은 실행하지 않고 `result.status: failed`를 반환한다. 서버는 배포 실패를 `module_records`와 `system_logs`에 기록한다. |
| 플러그인 → 서버 | `action` | 플러그인 UI에서 사용자가 발생시킨 페이지 전송, 스크린샷 전송, 프로젝트 실행 등 요청을 서버에 전달한다. | 승인된 플러그인 토큰, 사용자 액션 권한, 액션-모듈 매핑 권한, 필요한 브라우저 manifest 권한. | 요청: `action` / 응답: 서버의 수락·거절 결과 또는 후속 `result`/상태 이벤트 | 알 수 없는 액션, 권한 부족, payload 검증 실패, 중복 멱등 키 충돌 시 `status: denied` 또는 `failed`와 표준 오류 코드를 반환한다. 서버 실행이 필요한 경우 실패 job 상태를 기록한다. |
| 플러그인 → 서버 | `result` | 브라우저 실행 모듈 또는 플러그인 측 처리 결과를 서버에 반환한다. | 승인된 플러그인 토큰, 해당 `correlation_id`/`execution_id`에 대한 결과 제출 권한. | 요청: `push_module` 또는 `terminate`의 후속 / 응답: 서버 저장 수락 결과 | 결과 스키마 오류, 알 수 없는 실행 ID, 저장 실패 시 서버는 `failed` 응답을 반환하고 재시도 가능 여부를 표시한다. 저장 전 중복 결과는 멱등 처리한다. |
| 서버 → 플러그인 | `terminate` | 실행 중인 브라우저 모듈 또는 플러그인 측 작업을 중단하도록 지시한다. | `operator` 이상 강제 종료 권한 또는 서버 watchdog/정책 엔진 권한. | 요청: `terminate` / 응답: `terminated` 또는 실패 `result` | 대상 실행을 찾을 수 없거나 이미 종료된 경우 멱등 성공으로 처리할 수 있다. 종료 실패나 제한 시간 초과 시 `terminated.status: failed`와 원인을 기록한다. |
| 플러그인 → 서버 | `terminated` | 플러그인이 `terminate` 처리 결과와 실제 종료 시각을 서버에 보고한다. | 승인된 플러그인 토큰, 대상 실행에 대한 종료 보고 권한. | 요청: `terminate` / 응답: `terminated` | 종료 보고가 누락되면 서버 watchdog이 타임아웃으로 실행 상태를 닫고 Warning/Critical 알림을 발생시킨다. |
| 양방향 | `refresh` | 토큰 갱신, 재연결 시 누락 이벤트 복구, 세션 상태 재동기화를 요청·응답한다. | 기존 토큰 또는 refresh token, 플러그인 식별자 검증 권한. | 요청: `refresh` / 응답: `refresh` | 토큰 만료·폐기·불일치 시 `status: expired` 또는 `denied`를 반환한다. 이벤트 커서가 만료되면 상태 스냅샷 재동기화를 요구한다. |

#### `execute` 처리 원칙

`execute`는 공개 메시지 타입으로 사용하지 않는다. 관리자 즉시 실행 요청은 관리자 API에서 서버 내부 job으로 생성하고, 서버 런타임 모듈은 job 워커가 직접 처리한다. 브라우저에서 실행해야 하는 경우에만 job 결과로 `push_module`을 생성해 대상 플러그인에 배포한다. 따라서 플러그인 명령은 `push_module`, 사용자 발생 요청은 `action`, 서버 내부 작업은 job 모델로 구분한다.

### 5.2 MCP 및 Action 메시지 처리 방식

MCP(Model Context Protocol) 기반 도구 호출과 플러그인 UI `action` 이벤트는 동일한 공통 메시지 envelope를 사용한다. 서버는 메시지 envelope를 먼저 검증한 뒤 `type`에 따라 MCP 도구 실행, 브라우저 모듈 푸시, 서버 내부 job 생성·상태 갱신, 종료, 결과 기록, 토큰 갱신 흐름으로 라우팅한다.

#### 공통 메시지 envelope

모든 WebSocket/HTTP 메시지는 다음 필드를 최상위에 포함해야 한다.

| 필드 | 필수 | 설명 |
| --- | --- | --- |
| `schema_version` | 예 | 메시지 스키마 버전. 예: `1.0.0` |
| `message_id` | 예 | 메시지별 전역 고유 ID. UUID v4 또는 ULID 사용 권장 |
| `correlation_id` | 예 | 하나의 요청-응답-후속 이벤트를 연결하는 상관관계 ID |
| `plugin_id` | 예 | 승인된 플러그인 식별자 |
| `timestamp` | 예 | ISO 8601 UTC 생성 시각 |
| `type` | 예 | `push_module`, `action`, `result`, `terminate`, `terminated`, `refresh` 등 메시지 타입 |
| `auth` | 예 | 인증 및 무결성 검증 정보 |
| `payload` | 예 | 타입별 업무 데이터. 데이터가 없으면 빈 객체 `{}` 사용 |

`auth` 객체는 JWT 또는 세션 토큰을 반드시 포함하고, 재전송·위변조 방지가 필요한 환경에서는 `nonce`와 `signature`를 추가한다.

```json
{
  "auth": {
    "scheme": "Bearer",
    "token": "jwt-or-session-token",
    "nonce": "base64url-random-nonce",
    "signature": "base64url-hmac-or-signature"
  }
}
```

서버가 플러그인에 반환하는 응답성 메시지(`result`, `terminated`, `refresh` 응답 및 명령 수락/거절 응답)는 `payload` 내부 또는 타입별 응답 본문에 다음 필드를 포함해야 한다.

| 필드 | 필수 | 설명 |
| --- | --- | --- |
| `status` | 예 | `accepted`, `success`, `failed`, `denied`, `expired` 등 처리 상태 |
| `error_code` | 예 | 오류가 없으면 `null`, 오류가 있으면 표준 오류 코드 |
| `error_message` | 예 | 오류가 없으면 `null`, 오류가 있으면 사용자/운영자용 요약 메시지 |
| `retryable` | 예 | 동일 요청 재시도 가능 여부 |

#### 멱등 처리 규칙

- 수신자는 `plugin_id + message_id` 조합을 기준으로 중복 메시지를 탐지하고, 동일 메시지가 다시 도착하면 이미 저장된 처리 결과를 반환하거나 무시한다.
- 업무상 같은 명령을 여러 번 전송할 수 있는 `action`, `push_module`, `terminate` 메시지는 `payload.idempotency_key`를 추가로 지원한다.
- `idempotency_key`가 있으면 `plugin_id + type + idempotency_key`를 우선 멱등 키로 사용하고, 없으면 `plugin_id + message_id`를 사용한다.
- 멱등 키 저장소에는 처리 상태, 최종 응답, 만료 시각을 기록하며, 최소 보존 기간은 재시도 정책의 최대 기간보다 길게 설정한다.
- 멱등 키가 같지만 `payload` 해시가 다르면 중복이 아니라 충돌로 판단하고 `status: "failed"`, `error_code: "IDEMPOTENCY_CONFLICT"`, `retryable: false`를 반환한다.

#### 연결 재시도 및 누락 이벤트 복구 정책

- 플러그인은 재연결 시 마지막으로 성공 처리한 서버 이벤트의 `message_id`를 `payload.last_processed_message_id`에 담아 `refresh` 또는 재동기화 요청을 보낸다.
- 서버는 플러그인별 송신 이벤트 로그에서 `last_processed_message_id` 이후의 미확인 이벤트를 조회해 순서대로 재전송한다.
- 서버가 해당 `message_id`를 보존 기간 초과로 찾을 수 없으면 전체 상태 스냅샷 재동기화를 요구하고 `error_code: "EVENT_CURSOR_EXPIRED"`, `retryable: true`를 반환한다.
- 재전송 이벤트도 원본 `message_id`와 `correlation_id`를 유지해야 하며, 수신자는 멱등 처리 규칙으로 중복 실행을 방지한다.
- 이벤트 순서는 `timestamp`만으로 판단하지 않고 서버가 보관하는 단조 증가 sequence 또는 이벤트 로그 offset을 기준으로 복구한다.

### 5.4 실행 단계

1. 플러그인이 `register` 메시지를 전송한다.
2. 서버가 승인 후 JWT 토큰을 발급한다.
3. 플러그인은 토큰을 사용해 인증된 상태로 대기한다.
4. 관리자가 모듈을 푸시하거나 사용자가 플러그인 UI에서 액션을 실행한다.
5. 서버는 공통 envelope와 `auth`를 검증하고 `message_id` 또는 `idempotency_key`로 중복 여부를 확인한다.
6. 서버는 모듈 정의와 런타임에 따라 실행 엔진을 선택한다.
7. 실행 결과는 공통 envelope를 적용한 `result` 또는 서버 응답 메시지로 반환하고, 모듈 DB와 메인 DB에 기록한다.
8. 종료 또는 오류 이벤트는 알림 시스템으로 전달된다.
9. 연결이 끊긴 플러그인은 재연결 후 마지막 처리 `message_id`를 제출하고, 서버는 누락 이벤트를 복구한다.

### 필수 요구사항

- 모든 메시지는 `schema_version`, `message_id`, `correlation_id`, `plugin_id`, `timestamp`, `type`, `auth`, `payload`를 포함해야 한다.
- `auth`는 JWT 또는 세션 토큰을 포함하고, 필요 시 `nonce`와 `signature`로 재전송·위변조를 방지해야 한다.
- 서버 응답 메시지는 `status`, `error_code`, `error_message`, `retryable`을 포함해야 한다.
- 결과 메시지는 성공/실패 상태와 최소 오류 정보를 포함해야 한다.
- 중복 메시지는 `message_id` 또는 `idempotency_key` 기준으로 멱등 처리해야 한다.
- 재연결 시 마지막 처리 `message_id` 기준으로 누락 이벤트를 복구해야 한다.

### 권장 사항

- 메시지 스키마 버전을 포함해 하위 호환성을 관리한다.
- 재시도 가능한 오류와 재시도 불가능한 오류를 구분한다.

### 향후 아이디어

- 메시지 스키마를 JSON Schema로 관리하고 CI에서 호환성 검사를 수행한다.

## 6. 보안 아키텍처

### 6.1 토큰 기반 인증

- 플러그인 등록 승인 시 서버는 **access token과 refresh token을 분리해 발급**한다. access token은 WebSocket/HTTP 요청 인증과 권한 검증에만 사용하고, refresh token은 access token 재발급과 세션 유지에만 사용한다. 단일 장기 JWT만 사용하는 방식은 탈취 시 피해 범위가 크므로 금지한다.
- access token은 서명된 JWT로 발급하며 수명은 짧게 유지한다. 기본 만료 시간은 15분, 운영 허용 범위는 5~30분으로 한다. refresh token은 난수 기반 opaque token 또는 refresh 전용 JWT로 발급하며 기본 만료 시간은 14일, 운영 허용 범위는 7~31일로 한다.
- access token과 refresh token에는 최소한 `plugin_id`, `aud`, `iss`, `exp`, `iat`, `jti`, 권한 `scope`를 포함한다. `aud`는 WebSocket/API 등 대상 서비스를, `iss`는 발급 서버를, `jti`는 토큰별 고유 식별자와 재사용 감지 키를 의미한다.
- DB에는 refresh token 원문을 저장하지 않는다. `tokens` 또는 세션 테이블에는 refresh token의 `jti`, 만료 시각, 발급 플러그인, 디바이스/설치 식별자, 상태값, 그리고 Argon2id 또는 PBKDF2/bcrypt 같은 비밀번호 저장용 KDF로 계산한 refresh token 해시만 저장한다. 원문 토큰은 발급 직후 플러그인에 1회 전달하고 서버 로그, 감사 로그, 오류 메시지에 기록하지 않는다.
- 모든 요청은 `plugin_id + access token`을 검증하고, 토큰의 서명, `exp`, `iat`, `iss`, `aud`, `jti`, 폐기 여부, 플러그인 승인 상태, `scope`를 함께 확인한다. WebSocket은 연결 수립(handshake) 시 인증·권한 검증을 수행하고, 연결 유지 중에도 `action`, `push_module`, `result`, `terminate`, `refresh` 등 중요 메시지를 처리할 때마다 메시지별 인증·권한 검증을 다시 수행한다.
- 만료 1일 전 또는 access token 만료 직전 자동 갱신 요청(`refresh`)을 처리한다. refresh 요청은 refresh token으로만 허용하며, access token만으로 refresh token을 재발급하지 않는다.
- refresh token은 **회전(rotation)** 방식으로 운영한다. 정상 refresh가 성공하면 기존 refresh token의 `jti`를 즉시 `rotated` 또는 `revoked` 상태로 바꾸고, 새 refresh token과 새 access token을 발급한다. 동시 요청 허용을 위해 최대 30~60초의 짧은 grace window를 둘 수 있으나, grace window 내에도 동일 `jti` 사용 횟수와 요청 출처를 기록한다.
- 이미 회전·폐기·만료된 refresh token이 다시 제출되면 refresh token 재사용 공격으로 간주한다. 재사용 감지 시 해당 refresh token 체인과 동일 플러그인 설치 인스턴스의 전체 세션을 즉시 폐기하고, 관련 access token `jti`를 차단 목록에 등록하며, WebSocket 연결을 종료하고 Critical 보안 알림과 감사 로그를 생성한다.
- 플러그인 승인 취소, 플러그인 분실, 토큰 탈취 의심, 관리자 수동 차단, 비정상 위치·기기·사용 패턴 탐지 시 revoke 절차를 수행한다. 절차는 ① 대상 `plugin_id`와 설치/세션 범위 식별, ② `browser_plugins` 상태를 `revoked`, `lost`, `suspended` 등으로 변경, ③ 관련 refresh token 해시 레코드와 access token `jti`를 `revoked`로 표시 또는 차단 목록 등록, ④ 활성 WebSocket 세션 강제 종료, ⑤ 진행 중 작업 중단 또는 격리, ⑥ 관리자·보안 채널 알림, ⑦ `system_logs`와 감사 로그에 사유·처리자·시각·영향 범위 기록 순서로 수행한다.
- revoke 이후 플러그인이 재등록하려면 관리자 재승인과 새 등록 nonce/등록 키 발급을 거쳐야 하며, 기존 refresh token 체인은 재사용할 수 없다.

### 6.2 실행 검증

- JavaScript 모듈은 Web Worker에서 실행한다.
- DOM, 쿠키, 세션 접근은 제한한다.
- Node.js, Python, Windows 실행 모듈은 리소스 사용량을 실시간 모니터링한다.
- Windows 실행 모듈은 관리자 승인, 코드 서명 검증 또는 해시 allowlist 검증(§3.3), 실행 환경 검증을 거친다.
- 배포 전 샌드박스 테스트 자동화로 무한 루프와 악성 코드를 사전에 차단한다.

#### 리소스 기반 종료 임계값 (기본값)

7.2의 자동 재시작 정책(10분/3회)처럼, 리소스 기반 자동 종료도 실제 구현 가능한 숫자를 모듈 정책 기본값으로 둔다. 모듈별로 `resource_limits` 설정에서 아래 기본값을 override할 수 있다.

| 리소스 | 경고(Warning) 임계값 | 강제 종료(Critical) 임계값 | 판정 방식 |
| --- | --- | --- | --- |
| CPU | 프로세스 기준 70% 초과가 30초 이상 지속 | 90% 초과가 15초 이상 지속 | watchdog이 1초 간격 샘플링한 이동평균 |
| 메모리 | 프로세스 기준 512MB 초과 | 1,024MB(1GB) 초과 | RSS(Resident Set Size) 기준 |
| 네트워크 아웃바운드 | 5MB/s 초과가 10초 이상 지속 | 20MB/s 초과 또는 목적지가 allowlist 도메인 외부 | watchdog이 소켓 통계를 폴링 |
| 실행 시간 | 모듈 정책의 타임아웃 80% 경과 | 타임아웃 100% 경과 | §7.2 타임아웃 종료와 동일 |

`windows_exec`처럼 위험도가 높은 런타임은 위 기본값보다 낮은 한도(예: CPU 50%/70%, 메모리 256MB/512MB)를 모듈 정책에서 별도로 지정하는 것을 권장한다. 임계값 초과 시 처리(경고 알림만 발생 vs 즉시 종료)는 §7.2의 리소스 기반 종료 절차를 따른다.

### 6.3 관리자 권한

- 관리자 페이지 접근은 인증된 관리자 로그인 기반으로 제한한다.
- 역할은 `super-admin`, `operator`, `auditor`, `developer` 등으로 세분화한다.
- OS 내부 프로그램 실행은 `super-admin` 권한에서만 허용한다.
- 로컬 1인 운영 환경에서는 역할을 단일 관리자 계정으로 단순화할 수 있다(§3.3 "개인 단독 운영 시 권한 모델 간소화" 참고). 다만 OS 내부 프로그램 실행에 대한 승인 절차 자체는 생략하지 않는다.

### 6.4 로컬 서버 접근 통제

서버가 로컬 1대에서만 동작하더라도, 브라우저가 방문하는 임의의 웹페이지는 그 브라우저 안에서 JavaScript로 `ws://localhost:PORT` 또는 `wss://localhost:PORT`에 연결을 시도할 수 있다(localhost 대상 Cross-Site WebSocket Hijacking / DNS 리바인딩 패턴). 따라서 "개인이 로컬에서만 쓴다"는 사실이 이 위협을 제거하지 않으며, 아래 통제는 운영 규모와 무관하게 항상 적용한다.

- 서버는 `0.0.0.0`이 아니라 **loopback 주소(`127.0.0.1`)에만 바인딩**한다. LAN·외부 네트워크에서의 접근이 필요해지기 전까지는 바인딩 주소를 넓히지 않는다.
- WebSocket handshake 시 `Origin` 헤더를 검증하고, 알려진 확장 프로그램 오리진(`chrome-extension://<고정 확장 ID>`)만 allowlist로 허용한다. Origin이 없거나 allowlist 밖이면 handshake 단계에서 즉시 거부한다.
- `plugin_id + access token` 검증(§6.1)은 Origin 검증과 별개로 항상 유지한다. 두 검증은 서로 다른 공격을 막으므로 하나로 대체하지 않는다.
- 관리자 UI(웹 페이지)를 별도로 둔다면, 관리자 UI 역시 loopback 바인딩과 별도 세션 인증을 적용하고 WebSocket 게이트웨이와 동일한 포트를 공유하지 않는 것을 권장한다.

### 필수 요구사항

- 서버는 기본적으로 loopback(`127.0.0.1`)에만 바인딩하며, 외부 바인딩은 별도 설정과 관리자 승인을 거친다.
- WebSocket handshake는 `Origin` allowlist 검증을 통과해야 연결을 수립한다.

- 권한 없는 사용자는 모듈 등록, 실행, 종료, 저장 경로 변경을 수행할 수 없다.
- 실행 전 검증 실패 시 모듈 실행을 차단하고 Critical 또는 Warning 알림을 발생시킨다.

### 권장 사항

- Zero Trust 모델에 따라 매 요청마다 권한과 토큰 상태를 검증한다.
- 관리자 중요 작업은 감사 로그와 변경 전후 값을 모두 기록한다.

### 향후 아이디어

- 이상 행위 탐지 모델을 적용해 비정상 실행 패턴을 자동 차단한다.

## 7. 운영 관리 전략

### 7.1 플러그인 모니터링

관리 페이지는 플러그인 소켓 연결 상태, 브라우저 정보, 마지막 활동 시간, 승인 상태를 표시한다. 비정상 종료나 연결 끊김이 발생하면 상단 알림 바에 Critical Priority 알림을 표시한다.

### 7.2 작업 종료 처리

- 정상 종료: 플러그인이 `result` 메시지를 전송하고 서버가 결과를 기록한다.
- 강제 종료: 관리자가 “작업 종료” 버튼을 클릭하면 서버가 `terminate` 메시지를 전송한다.
- 타임아웃 종료: 서버가 설정된 타임아웃을 초과한 작업에 자동으로 `terminate`를 전송한다.
- 리소스 기반 종료: CPU, 메모리, 네트워크 지연, 비정상 패킷 탐지 시 자동 종료 또는 재시작한다.
- 모듈별 자동 재시작 정책은 `max_restart_count`와 `restart_window_seconds`로 정의한다. 기본값은 10분(600초) 내 3회까지 허용하며, 시간 창 안에서 3회를 초과하면 해당 실행은 `restart_suspended` 상태로 중단한다. 위험도가 높은 `windows_exec` 또는 외부 시스템에 부하를 줄 수 있는 모듈은 더 낮은 한도를 적용한다.
- 재시작 간격은 exponential backoff를 적용한다. 예를 들어 기본 지연 5초에서 시작해 10초, 20초, 40초처럼 증가시키고, 모듈 정책의 `max_backoff_seconds`를 초과하지 않도록 제한한다.
- 동일 모듈에서 동일 오류 코드 또는 동일 종료 코드가 정책 기준 이상 반복되면 상태를 `circuit_open`으로 전환한다. `circuit_open` 상태의 모듈은 관리자 승인 또는 명시적인 회로 해제 조치 전까지 자동 재시작과 수동 재실행을 모두 차단한다.
- 재시작 시도마다 성공(`restart_succeeded`), 실패(`restart_failed`), 한도 초과 중단(`restart_suspended`), 회로 차단(`circuit_open`) 상태를 메인 DB `module_records`와 모듈 DB `execution_logs`에 동일한 `run_id`와 `correlation_id`로 기록한다. 기록에는 재시작 횟수, 시간 창 시작 시각, 다음 backoff 지연, 오류 코드, 종료 코드, 승인자 정보를 포함한다.

### 7.3 알림 시스템

알림 시스템은 모든 운영 이벤트를 동일한 메타데이터 스키마로 기록하고, 심각도(`severity`)와 사용자 필터 정책에 따라 관리자 UI 및 외부 메신저 전송 여부를 결정한다. 정상 종료는 기본적으로 `Info`로 분류하며, 사용자 요청에 따른 강제 종료는 운영 정책에 따라 `Warning` 또는 `Info`로 분류한다. 오류, 보안 위반, 재시작 실패, 데이터 저장 실패, 플러그인 비정상 종료는 반드시 `Critical`로 분류한다.

#### 알림 공통 필드

| 필드 | 설명 | 예시 |
| --- | --- | --- |
| `severity` | 알림 심각도. `Critical`, `Warning`, `Info` 중 하나를 사용한다. | `Critical` |
| `category` | 알림 유형. 종료, 보안, 저장, 재시작, 성능, 연결, 설정 등 운영 분류를 기록한다. | `termination`, `security`, `storage` |
| `dedup_key` | 동일 원인 알림을 중복 발송하지 않기 위한 키. `plugin_id`, `module_id`, `run_id`, 이벤트 원인을 조합한다. | `plugin-123:module-7:storage_failed` |
| `ack_required` | 관리자 확인 필요 여부. `Critical`은 기본 `true`, `Warning`/`Info`는 정책에 따라 설정한다. | `true` |
| `escalation_policy` | 미확인 또는 반복 발생 시 상위 채널·담당자·온콜로 확대하는 정책 식별자다. | `critical_oncall_15m` |

#### 심각도 기준

| severity | 적용 이벤트 | 기본 확인 정책 | 기본 확대 정책 |
| --- | --- | --- | --- |
| `Critical` | 오류 발생, 보안 위반, 작업 종료 실패, 재시작 실패, 데이터 저장 실패, 플러그인 비정상 종료 | `ack_required=true` | 즉시 관리자 UI 고정 표시, 미확인 시 온콜 또는 상위 채널로 확대 |
| `Warning` | 사용자 요청에 따른 강제 종료를 경고로 운영하는 정책, 성능 저하, 비정상 연결, 타임아웃 종료, 리소스 기반 자동 종료 | 정책별 설정 | 반복 발생 또는 임계치 초과 시 확대 |
| `Info` | 정상 종료, 사용자 요청에 따른 강제 종료를 정보로 운영하는 정책, 설정 변경, 일반 상태 변경 | 기본 `ack_required=false` | 일반적으로 확대하지 않음 |

#### 전송 채널 및 필터 정책

- 관리자 페이지 상단 알림 바와 toast/notification 컴포넌트는 모든 severity를 표시하되, `Critical`은 최상단 고정 또는 동등한 수준의 즉시 인지 UI로 표시한다.
- Slack, 텔레그램, 카카오톡 전송 여부는 `severity`와 사용자별·조직별 필터 정책에 따라 결정한다. 예를 들어 기본 정책은 `Critical` 즉시 전송, `Warning` 조건부 전송, `Info` 미전송으로 둘 수 있다.
- 사용자 필터 정책은 severity, category, plugin_id, module_id, 업무 시간, 담당 그룹, 반복 횟수, `ack_required` 여부를 조건으로 지원한다.
- 동일 `dedup_key`를 가진 알림은 지정된 집계 기간 동안 중복 전송을 억제하고, 발생 횟수와 마지막 발생 시각을 갱신한다.
- `escalation_policy`는 미확인 시간, 반복 발생 횟수, 업무 시간 외 여부에 따라 Slack/텔레그램/카카오톡, 이메일, 온콜 로테이션 등으로 확대할 수 있다.

알림 폭주를 방지하기 위해 동일 `module_id`, `error_code`, `termination_reason`, `correlation_id` 또는 동일 원인 해시를 가진 알림은 지정된 집계 시간 동안 하나의 그룹으로 묶거나 채널별 rate limit을 적용한다. 그룹화된 알림에는 최초 발생 시각, 마지막 발생 시각, 누적 건수, 대표 실행 ID를 포함한다.

### 7.4 로그 및 분석

- 모든 명령 실행 기록은 `system_logs`와 `module_records`에 저장한다.
- 모듈별 실행 기록은 모듈 DB의 `execution_logs`에 저장한다.
- 알림 로그는 acknowledged 여부를 포함한다.
- 장기적으로 ELK Stack과 연동해 성능 및 에러 패턴을 시각화한다.

### 필수 요구사항

- 정상 종료, 강제 종료, 자동 종료는 모두 모듈 DB와 메인 DB에 기록한다.
- Critical 알림은 관리자 UI에서 즉시 인지 가능해야 한다.

### 권장 사항

- 알림 피로도를 줄이기 위해 Warning/Info 알림에는 사용자 정의 필터링 옵션을 제공한다.
- 자동 재시작은 모듈별 재시도 횟수, 시간 창, exponential backoff, circuit breaker 조건을 함께 제한한다.
- 동일 원인 알림에는 그룹화 또는 rate limit을 적용해 Critical 알림 폭주와 외부 메신저 과금을 방지한다.

### 향후 아이디어

- 알림 처리 시간과 acknowledged 데이터를 분석해 운영 SLA를 측정한다.

### 향후 아이디어

## 9. 시스템 안정성 확보 전략

### 9.1 데이터 일관성

실행 결과, 시스템 로그, 알림 로그는 하나의 트랜잭션 단위로 처리하는 것을 원칙으로 한다.

```sql
BEGIN TRANSACTION;

INSERT INTO execution_logs (module_id, status, output_path, execution_time, created_at)
VALUES (101, 'SUCCESS', '/data/pages/project_A/result.html', 4.8, CURRENT_TIMESTAMP);

INSERT INTO system_logs (event_type, message, timestamp)
VALUES ('EXECUTION', '프로젝트 A 실행 완료', CURRENT_TIMESTAMP);

INSERT INTO alert_logs (module_id, severity, category, dedup_key, message, ack_required, acknowledged, created_at)
VALUES (101, 'Info', 'execution', 'plugin-123:module-101:success', '프로젝트 A 실행 성공', FALSE, FALSE, CURRENT_TIMESTAMP);

COMMIT;
```

오류 발생 시 `ROLLBACK`을 수행하고 Critical 알림을 발생시킨다.

위 예시의 `alert_logs` 컬럼은 §7.3 "알림 공통 필드"에서 정의한 스키마(`severity`, `category`, `dedup_key`, `ack_required` 등)와 동일하며, 전체 컬럼 목록은 부록 E를 따른다. 이전 버전 예시에 있던 `priority` 컬럼명은 §7.3의 공식 필드명인 `severity`로 통일했다.

### 9.2 ACID 관점

- 원자성: 실행 결과, 시스템 로그, 알림 로그는 모두 성공하거나 모두 취소된다.
- 일관성: FK, CHECK 제약 조건으로 잘못된 상태나 우선순위를 차단한다.
- 격리성: 동시 실행 요청의 결과와 로그가 뒤섞이지 않도록 격리 수준을 관리한다.
- 지속성: 커밋된 실행 결과와 로그는 장애 후에도 복구 가능해야 한다.

### 필수 요구사항

- 트랜잭션 실패 시 부분 저장을 방지한다.
- 서버 장애 후 DBMS의 Undo/Redo 로그 기반 복구를 고려한다.

### 권장 사항

- 실행 요청마다 idempotency key를 부여해 중복 실행을 방지한다.
- 장애 시 사용자와 관리자에게 서로 다른 상세 수준의 오류 메시지를 제공한다.

### 향후 아이디어

# 부록 B. 저장 경로 설계

## B.1 환경 설정 테이블

```sql
CREATE TABLE module_settings (
  module_id INTEGER PRIMARY KEY,
  page_dir TEXT,
  image_dir TEXT,
  video_dir TEXT,
  updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

- `page_dir`: HTML/페이지 저장 경로
- `image_dir`: 스크린샷 및 이미지 저장 경로
- `video_dir`: 동영상 저장 경로
- 모든 모듈별 저장 경로는 전역 `storage_root` 하위 디렉토리만 허용한다.
- `storage_root`는 운영자가 서버 설정에서 고정한 절대 경로이며, 관리자 UI에서 입력하는 모듈별 경로는 `storage_root` 내부의 상대 하위 경로 또는 정규화 후 `storage_root` 하위로 판정되는 경로여야 한다.

## B.2 관리자 UI 예시

```html
<form method="POST" action="/admin/module/settings/update">
  <label>페이지 저장 경로</label>
  <input type="text" name="page_dir" value="pages/module_1/">

  <label>이미지 저장 경로</label>
  <input type="text" name="image_dir" value="images/module_1/">

  <label>동영상 저장 경로</label>
  <input type="text" name="video_dir" value="videos/module_1/">

  <button type="submit">저장</button>
</form>
```

- 관리자 UI에는 전역 `storage_root`를 기준으로 한 하위 경로만 입력하도록 안내한다.
- 서버는 관리자 입력값을 그대로 신뢰하지 않고 저장 전에 `realpath` 정규화와 allowlist 검증을 수행한다.

## B.3 서버 실행 로직 예시

```javascript
const fs = require("fs");
const path = require("path");
const { randomUUID } = require("crypto");

const STORAGE_ROOT = "/data/storage";
const EXTENSION_ALLOWLIST = {
  page: ".html",
  image: ".png",
  video: ".mp4",
};

function resolveAllowedDir(storageRoot, configuredDir) {
  const rootRealPath = fs.realpathSync(storageRoot);
  const candidatePath = path.join(rootRealPath, configuredDir);
  const candidateRealPath = fs.realpathSync(candidatePath);

  if (!candidateRealPath.startsWith(rootRealPath + path.sep)) {
    throw new Error("storage path is outside storage_root");
  }

  return candidateRealPath;
}

function saveResult(moduleId, runId, artifactId, type, dataBuffer, detectedMimeType) {
  const settings = getModuleSettings(moduleId);
  const targetDir = resolveAllowedDir(STORAGE_ROOT, settings[`${type}_dir`]);
  const extension = EXTENSION_ALLOWLIST[type];

  validateMimeType(type, detectedMimeType);
  validateFileSize(type, dataBuffer.length);
  validateDiskQuota(moduleId, dataBuffer.length);

  const safeFileName = `${runId}-${artifactId}-${randomUUID()}${extension}`;
  const targetPath = path.join(targetDir, safeFileName);

  fs.writeFileSync(targetPath, dataBuffer, { flag: "wx" });
}
```

- 예시 코드와 실제 구현 모두 문자열 템플릿이나 단순 문자열 덧셈으로 파일 경로를 결합하지 않고 `path.join`, `path.resolve`, `Path.Combine`, `java.nio.file.Path` 등 플랫폼 안전 API를 사용한다.
- `fs.writeFileSync(..., { flag: "wx" })`처럼 원자적 생성 옵션을 사용해 기존 파일을 덮어쓰지 않는 것을 기본 중복 파일 처리 규칙으로 삼는다.

## B.4 저장 경로 변경 시나리오

1. 관리자가 모듈 상세 페이지의 환경 설정 메뉴로 이동한다.
2. 페이지, 이미지, 동영상 저장 경로를 입력한다.
3. 서버가 입력 경로를 `realpath`로 정규화하고 `storage_root` allowlist 하위인지 검증한다.
4. 서버가 `module_settings` 테이블을 업데이트한다.
5. 변경 내역을 `system_logs`에 기록한다.
6. 알림 바와 외부 메신저에 Info 알림을 전송한다.
7. 이후 모듈 실행 결과는 새 경로에 저장된다.

```sql
UPDATE module_settings
SET page_dir = 'pages/module_A/',
    image_dir = 'images/module_A/',
    video_dir = 'videos/module_A/',
    updated_at = CURRENT_TIMESTAMP
WHERE module_id = 1;
```

## B.5 경로 검증 및 파일 저장 보안 규칙

- 저장 경로 allowlist는 전역 `storage_root`의 `realpath`와 모듈별 허용 하위 디렉토리 목록으로 구성한다.
- 관리자 입력 경로는 저장 전 반드시 `realpath`로 정규화하고, 정규화된 결과가 allowlist 경로와 동일하거나 그 하위 디렉토리인지 확인한다.
- `..` 경로 세그먼트는 입력 단계에서 거부하며, 정규화 후에도 `storage_root` 밖으로 벗어나면 거부한다.
- 절대 경로 입력은 기본적으로 거부한다. 운영상 예외가 필요한 경우에도 `realpath` 검증 결과가 `storage_root` 하위이고 별도 allowlist에 등록된 경로일 때만 허용한다.
- 심볼릭 링크는 기본적으로 거부한다. 허용이 필요한 경우 링크의 최종 `realpath` 대상이 `storage_root` 하위이며 운영자가 등록한 allowlist 하위일 때만 허용한다.
- 네트워크 공유 경로(예: Windows UNC `\\server\\share`, SMB/NFS 마운트 경로)는 기본적으로 거부한다. 전용 스토리지로 운영하려면 `storage_root` 자체를 해당 마운트 지점으로 고정하고 별도 용량·권한·가용성 점검을 통과한 경우에만 허용한다.
- 파일명은 `run_id`, `artifact_id`, UUID 조합으로 서버가 생성하며, 사용자 또는 플러그인이 전달한 원본 파일명을 저장 파일명으로 직접 사용하지 않는다.
- 파일 저장 전 수집 데이터의 MIME/type을 서버 측에서 탐지하고 모듈·산출물 유형별 허용 MIME 목록과 일치하는지 검증한다.
- 파일 저장 전 산출물 유형별 최대 크기 제한을 검증하고, 초과 파일은 저장하지 않으며 표준 오류 코드와 감사 로그를 남긴다.
- 확장자는 산출물 유형별 allowlist에서만 선택하며, 클라이언트가 제공한 확장자를 신뢰하지 않는다.
- 저장 전 모듈별·전체 `storage_root` 디스크 quota와 남은 공간을 확인하고, quota 초과 시 저장을 거부하거나 사전 정의된 보존 정책에 따라 오래된 임시 파일만 정리한다.
- 중복 파일은 덮어쓰지 않는다. 동일 `run_id`·`artifact_id` 재시도는 기존 산출물 메타데이터를 조회해 멱등 성공으로 처리하거나 새 UUID 파일명으로 저장하고 중복 관계를 DB에 기록한다.

### 필수 요구사항

- 저장 경로 변경은 인증된 관리자만 수행할 수 있다.
- 경로 변경 내역은 `system_logs`와 알림 로그에 기록한다.
- 실행 시점에는 DB에서 최신 저장 경로를 조회한다.

### 권장 사항

- 경로 저장 전 접근 권한, 디스크 여유 공간, 경로 유효성을 검증한다.
- 기본 저장 디렉토리와 모듈별 오버라이드 정책을 분리한다.

### 향후 아이디어

- 저장 경로 사용량을 모니터링해 임계치 초과 시 자동 알림을 발생시킨다.

# 부록 E. 메인 DB(`main.db`) 통합 스키마 정의

## E.1 배경

기존 버전에서는 `main.db`의 테이블 컬럼 정의가 §4.1(역할 설명), §4.3(필수 요구사항 산문), §6.1(토큰 필드 산문), §7.3(알림 필드 표), §9.1(SQL 예시), 부록 B.1(`module_settings` DDL)에 흩어져 있었고, 그중 일부(`alert_logs`, `module_settings`)는 §4.1 테이블 목록에서 아예 누락돼 있었다. 이 부록은 흩어진 정의를 하나의 DDL로 통합한 **단일 진실 공급원(source of truth)**이다. 본문과 이 부록이 다르면 이 부록을 기준으로 한다.

## E.2 전체 DDL

```sql
-- 플러그인 등록 및 상태 관리
CREATE TABLE browser_plugins (
  plugin_id TEXT PRIMARY KEY,
  status TEXT NOT NULL CHECK (status IN ('pending','approved','denied','revoked','lost','suspended')),
  browser TEXT CHECK (browser IN ('chrome','edge','firefox')),
  browser_version TEXT,
  extension_version TEXT,
  install_id TEXT,
  registered_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  approved_at TIMESTAMP,
  last_seen_at TIMESTAMP,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- access/refresh 토큰 메타데이터 (§6.1). 원문 토큰이 아니라 jti와 KDF 해시만 저장한다.
CREATE TABLE tokens (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  plugin_id TEXT NOT NULL REFERENCES browser_plugins(plugin_id),
  install_id TEXT,
  jti TEXT NOT NULL UNIQUE,
  token_type TEXT NOT NULL CHECK (token_type IN ('access','refresh')),
  token_hash TEXT, -- refresh token만 해당 (Argon2id/PBKDF2/bcrypt), access token은 NULL
  status TEXT NOT NULL CHECK (status IN ('active','rotated','revoked','expired')),
  rotated_from_jti TEXT, -- 회전 체인 추적용, 최초 발급 시 NULL
  issued_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  expires_at TIMESTAMP NOT NULL
);

-- 모듈 정의 (§3.2, §5.1)
CREATE TABLE modules (
  module_id INTEGER PRIMARY KEY AUTOINCREMENT,
  name TEXT NOT NULL,
  description TEXT,
  version TEXT NOT NULL,
  runtime TEXT NOT NULL CHECK (runtime IN ('javascript_browser_worker','nodejs','python','windows_exec')),
  script TEXT, -- javascript_browser_worker에서만 사용, 서버 런타임은 NULL
  status TEXT NOT NULL DEFAULT 'draft' CHECK (status IN ('draft','approved','disabled')),
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 관리자 이벤트 및 시스템 이벤트 (§4.1)
CREATE TABLE system_logs (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  event_type TEXT NOT NULL,
  message TEXT NOT NULL,
  actor TEXT, -- 관리자 계정 또는 'system'
  correlation_id TEXT,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 모듈 실행 참조 기록 (§4.1, §4.3 통합본)
CREATE TABLE module_records (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  plugin_id TEXT NOT NULL REFERENCES browser_plugins(plugin_id),
  module_id INTEGER NOT NULL REFERENCES modules(module_id),
  run_id TEXT NOT NULL,
  runtime TEXT NOT NULL,
  correlation_id TEXT,
  status TEXT NOT NULL CHECK (status IN ('running','success','failed','terminated')),
  started_at TIMESTAMP NOT NULL,
  ended_at TIMESTAMP,
  module_db_path TEXT NOT NULL,
  artifact_base_path TEXT,
  checksum TEXT,
  archived_at TIMESTAMP,
  retention_until TIMESTAMP,
  UNIQUE (module_id, run_id)
);

-- 모듈별 저장 경로 환경 설정 — 전체 정의는 부록 B.1
-- CREATE TABLE module_settings ( ... ); -- 부록 B.1 참조

-- 알림 이력 (§7.3 알림 공통 필드와 동일 스키마)
CREATE TABLE alert_logs (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  module_id INTEGER REFERENCES modules(module_id),
  plugin_id TEXT REFERENCES browser_plugins(plugin_id),
  run_id TEXT,
  severity TEXT NOT NULL CHECK (severity IN ('Critical','Warning','Info')),
  category TEXT NOT NULL,
  message TEXT NOT NULL,
  dedup_key TEXT NOT NULL,
  ack_required BOOLEAN NOT NULL DEFAULT FALSE,
  acknowledged BOOLEAN NOT NULL DEFAULT FALSE,
  acknowledged_by TEXT,
  acknowledged_at TIMESTAMP,
  escalation_policy TEXT,
  occurrence_count INTEGER NOT NULL DEFAULT 1,
  first_occurred_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  last_occurred_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- windows_exec 승인된 실행 파일 목록 (§3.3 코드 서명/해시 allowlist)
CREATE TABLE windows_exec_allowlist (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  module_id INTEGER NOT NULL REFERENCES modules(module_id),
  exec_path TEXT NOT NULL,
  verification_method TEXT NOT NULL CHECK (verification_method IN ('code_signing','hash_allowlist')),
  sha256_hash TEXT, -- verification_method = hash_allowlist일 때 필수
  signer_subject TEXT, -- verification_method = code_signing일 때 필수
  approved_by TEXT NOT NULL,
  approved_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  status TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active','revoked'))
);
```

## E.3 인덱스 권장

```sql
CREATE INDEX idx_module_records_plugin ON module_records(plugin_id, created_at);
CREATE INDEX idx_module_records_module ON module_records(module_id, run_id);
CREATE INDEX idx_alert_logs_dedup ON alert_logs(dedup_key);
CREATE INDEX idx_tokens_plugin ON tokens(plugin_id, status);
```

### 필수 요구사항

- `main.db`를 새로 생성하는 구현은 본 부록의 DDL을 기준으로 하며, 본문 산문 설명과 컬럼 목록이 다르면 이 부록을 따른다.
- `module_settings`는 부록 B.1의 DDL을 그대로 사용한다(중복 정의하지 않음).

### 권장 사항

- 스키마 변경 시 이 부록을 먼저 갱신한 뒤 마이그레이션 스크립트를 작성한다.

### 향후 아이디어

- 이 DDL을 기준으로 `sqlite3 main.db < schema.sql` 형태의 초기화 스크립트를 저장소에 함께 배포한다.
