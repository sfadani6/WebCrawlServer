## 1. 작업 흐름도

```
docs/ask.md (요청)
    ↓
docs/todo.md (계획 등록)
    ↓
실행 및 완료
    ↓
docs/todo.history.md (결과 등록, 년월일시분초)
    ↓
docs/askLogs/파일명-년월일시분초.md (상세 처리 내용)
```

## 2. 파일별 역할
- **docs/ask.md**: 작업 요청을 자유 형식으로 기록. 처리 완료 후 결과를 함께 정리해 추적 가능하도록 유지한다.
- **docs/todo.md**: AI가 실행할 작업 계획을 구체적 단계로 기록한다. 상태를 최신으로 유지하며 아래 흐름을 따른다.
  - 작업 착수 시 해당 항목을 "진행 중"으로 표시한다.
  - 완료 시 요약을 `docs/todo.history.md`로 옮기고, `docs/todo.md`에서는 해당 항목을 제거한다.
  - 착수하지 않았거나 보류된 항목을 완료로 잘못 표시하지 않으며, 실제 진행 상태와 문서 내용이 어긋난 채 방치하지 않는다.
- **docs/todo.history.md**: 완료된 작업의 요약과 상세 이력 파일 링크를 기록한다. 포맷: 완료 일시(YYYY-MM-DD HH:MM:SS), 항목명, 상세파일명, 결과 요약.
- **docs/askLogs/작업이름-YYYYMMDDHHMMSS.md**: 상세 실행 내용, 수정 파일, 변경 결과와 함께 **왜 그렇게 변경했는지(변경 이유)** 를 기록한다. (`AGENTS.md` 2장 규칙에 따라 신규 작업 시작 시 이 폴더는 참조하지 않는다.)

## 3. 운영 절차
1. `docs/ask.md`에 요청 기술
2. `docs/todo.md`에 계획 작성(우선순위, 실행 단계 포함)
3. 계획에 따라 실행, 변경사항 추적(`docs/todo.md` 상태를 "진행 중"으로 갱신)
4. 4장 작업 종료 체크리스트를 모두 확인
5. `docs/todo.history.md`에 완료 기록 추가, `docs/askLogs/`에 상세 이력 생성(변경 이유 포함)
6. 설계 결정이 있었던 작업이면 5장 기준에 따라 ADR 작성 여부 판단
7. 모든 변경사항 Git 커밋
8. `docs/todo.md`에서 완료 항목 제거, 필요 시 규칙 문서 갱신

### 3.1 AI 자동 이력 관리 절차 (AI 전용)
> **목적**: 다른 AI 에이전트가 동일한 이력 관리 절차를 자동으로 수행할 수 있도록 표준화
> **적용 대상**: 모든 AI 작업 완료 후 자동 수행

#### AI 자동 수행 체크리스트
- [ ] **todo.md 업데이트**
  - 완료된 작업은 `진행 중인 작업` 및 `예정된 작업`에서 **제거**
  - 다음 우선순위 작업을 `진행 중인 작업`에 **이동**
  - `다음 단계` 섹션에서 완료된 항목 **제거**

- [ ] **askLogs 로그 파일 생성**
  - 파일명: `ask-YYYYMMDDHHMMSS.md`
  - 위치: `docs/askLogs/`
  - 필수 포함 내용:
    - 요청 정보 (로그 생성 일시, 관련 문서, 요청 유형)
    - 수행된 작업 (변경 내용, 파일 위치, 기능 상세)
    - 결과 (체크 항목, 상태, 비고)
    - 관련 Rule ID
    - 변경 이유

- [ ] **todo.history.md 업데이트**
  - 이력 포맷: `[완료] HH:MM:SS - 작업 이름`
  - 내용 포함:
    - 작업 항목
    - 변경 내용 (Bullet list)
    - 변경 이유
    - 결과
    - 관련 Rule
    - 담당 AI
  - 통계 갱신:
    - 총 이력 수 +1
    - 완료된 작업 수 +1
    - 마지막 업데이트 시간 갱신

## 4. 작업 종료 체크리스트
작업을 "완료"로 표시하기 전 아래 항목을 모두 확인한다. 하나라도 미완료 상태면 완료로 표시하지 않는다.

- [ ] 코드 컴파일/실행 확인
- [ ] Lint/포맷 확인(프로젝트에 도구가 설정된 경우)
- [ ] `coding.md`(R-011) 코드 작성 규칙 위반 여부 확인
- [ ] 관련 로그(`logs/`, `activity_logs`, `error_logs`) 확인
- [ ] `docs/todo.md`에서 완료 항목 제거
- [ ] `docs/todo.history.md` 기록
- [ ] `docs/askLogs/`에 상세 이력(변경 내용 + 변경 이유) 작성
- [ ] 설계 결정 사항이 있었다면 5장 기준으로 ADR 작성 여부 확인
- [ ] Git add/commit(및 필요 시 push) 완료

## 5. ADR(Architecture Decision Record) 작성 규정

"왜 A 대신 B를 선택했는지"를 남기지 않으면 이후 같은 논의가 반복될 수 있다. 아래 기준에 해당하는 작업은 ADR을 남긴다.

### 5.1 작성 대상
아래 중 하나에 해당하면 ADR을 작성한다.
- 대안이 2개 이상 있었고, 그중 하나를 선택한 근거를 남길 필요가 있는 경우(예: 특정 라이브러리 채택, 스키마 구조 선택, 워크플로우 제어 구조 설계)
- 규칙 문서(`docs/rule/` 하위 문서)의 기존 결정을 뒤집는 변경인 경우
- 되돌리기 어렵거나 비용이 큰 구조 변경인 경우

단순 버그 수정, 오탈자 수정, 문서 경로 정정처럼 대안 비교가 필요 없는 작업은 ADR 대상이 아니다. 이 경우 `docs/askLogs/`의 변경 이유 기록으로 충분하다.

### 5.2 작성 위치 및 형식
- 위치: `docs/decision/`
- 파일명: `NNNN-짧은-제목.md` (예: `0001-module-structure.md`), 번호는 4자리 일련번호로 순차 부여한다.
- 최소 포함 항목: 제목, 상태(제안/채택/폐기), 배경(문제 상황), 검토한 대안, 선택한 대안과 근거, 영향 범위.
- `docs/decision/`은 `AGENTS.md` 2장의 컨텍스트 로딩 예외 규칙과 동일하게 취급한다. 즉 새 작업 시작 시 폴더 전체를 훑어보지 않으며, 사용자가 특정 ADR 파일을 명시적으로 지정한 경우에만 열람한다. 다만 관련 규칙 문서(`docs/rule/` 하위)를 변경하는 작업에서는 해당 주제의 기존 ADR이 있는지 파일명 목록만 확인하고, 관련성이 있으면 그 파일 하나를 열람한다.

### 5.3 규칙 문서와의 관계
- ADR은 결정의 "기록"이고, `docs/rule/` 하위 문서는 결정의 "현재 유효한 규칙"이다. 두 문서의 역할이 다르므로, ADR을 작성했다고 규칙 문서 갱신을 생략하지 않는다. 규칙에 반영해야 하는 내용은 반드시 해당 `docs/rule/*.md` 파일도 함께 갱신한다.
