## 1. Git 작업 규칙
- 작업 완료 시 반드시 변경사항을 Git에 기록한다.
- `정리해줘` 요청 시:
  - 변경된 파일을 `git add`로 스테이징
  - 명확한 커밋 메시지로 `git commit` (Conventional Commits 스타일)
  - 현재 브랜치에 `git push origin <branch>` 실행
  - 버전 관리가 필요한 경우 `docs/CHANGELOG/CHANGELOG.[버전].md` 생성 및 `docs/CHANGELOG.md`/관련 문서 갱신
  - 규칙 문서 자체도 함께 갱신
- 원격 저장소가 설정되어 있지 않거나 푸시 권한이 없으면 즉시 보고한다.

### 1.1 브랜치 네이밍 규칙

1인 개발 도구이므로 복잡한 브랜치 전략(GitFlow 전체 등)은 적용하지 않되, 최소한의 네이밍 규칙은 아래와 같이 둔다.

| 접두어 | 용도 | 예시 |
|---|---|---|
| `feature/` | 신규 기능 개발 | `feature/scheduler-overlap-policy` |
| `fix/` | 버그 수정 | `fix/db-wal-lock` |
| `docs/` | 문서만 변경 | `docs/split-instructions` |
| `refactor/` | 기능 변경 없는 구조 개선 | `refactor/module-loader` |
| `release/` | 릴리스 준비 브랜치 | `release/1.2.0` |

### 1.2 릴리스/핫픽스
- **release/**: `main`(또는 운영 기준 브랜치)에 배포하기 전 최종 점검용 브랜치. 버전 번호를 포함한다.
- **hotfix/**: 운영 중 발견된 긴급 결함을 `main`에서 바로 분기해 수정하는 브랜치. 접두어는 `fix/`와 구분해 `hotfix/`를 사용한다(긴급도 표시 목적).

### 1.3 머지 규칙
- 1인 개발 환경이므로 별도 리뷰어 승인 절차는 두지 않는다. 다만 머지 전 4.5(workflow-management.md 4장) 작업 종료 체크리스트를 통과했는지 확인한다.
- `feature/`, `fix/`, `refactor/` 브랜치는 완료 후 기준 브랜치에 머지하고 삭제한다. 이력이 필요한 경우 삭제 대신 보관해도 무방하다.

### 1.4 태그 규칙
- 릴리스 시점에 `vX.Y.Z` 형식의 Git 태그를 남긴다(예: `v1.2.0`). 버전 번호 규칙은 2장을 따른다.

## 2. 버전 업데이트 프로세스
1. `docs/CHANGELOG/CHANGELOG.X.Y.Z.md` 파일 생성
2. `docs/CHANGELOG.md` 최신 버전 섹션 및 버전 목록 업데이트
3. 규칙 문서 자체가 변경된 경우 상단 버전 갱신(4장 형식 준수)

| 버전 유형 | 예시 | 사용 시기 |
|---|---|---|
| MAJOR (X.0.0) | 0.1.0 → 1.0.0 | 기존 기능 삭제, 호환성 깨짐 |
| MINOR (1.Y.0) | 1.0.0 → 1.1.0 | 새 기능 추가(하위 호환) |
| PATCH (1.0.Z) | 1.0.0 → 1.0.1 | 버그 수정만 |

## 3. 버전 정리 체크리스트
- [ ] 모든 변경 사항이 코드에 반영됨
- [ ] 주석과 문서화 완료
- [ ] `docs/CHANGELOG/CHANGELOG.X.Y.Z.md` 생성
- [ ] `docs/CHANGELOG.md` 업데이트
- [ ] 규칙 문서 버전 업데이트(4장 형식 준수, 필요 시)
- [ ] Git commit 메시지 작성: `chore: version bump 1.0.0 → 1.1.0`

## 4. 문서 버전 기록 형식

규칙 문서(`AGENTS.md`, `docs/rule/*.md`)를 수정할 때는 상단에 아래 항목을 함께 기록한다.

- **Version**: 예) `1.3.0` (2장 버전 유형 기준)
- **작성자**: 최초 작성/수정한 주체. 1인 개발 프로젝트이므로 통상 "사용자" 또는 "AI 에이전트(사용자 승인)"로 기록한다.
- **수정일**: 예) `2026-07-25`
- **검토일**: 마지막으로 내용을 검토/확인한 날짜. 최초 작성 시에는 수정일과 동일하게 기록한다.
- **수정 이유**: 변경 내용을 한 줄로 요약하되, 여러 항목을 변경한 경우 항목을 나열한다.
- **관련 문서**: 이 문서와 직접 연결된 다른 규칙 문서(예: `docs/rule/xxx.md(R-00N)`).
- **영향 범위**: 이번 변경이 영향을 주는 파일/문서 범위.
- **Breaking Change 여부**: 기존 규칙/스키마/구조와 호환되지 않는 변경인지 여부와, 있다면 무엇이 깨지는지 한 줄로 명시.

버전 숫자만 올리고 나머지 항목을 갱신하지 않는 것은 허용하지 않는다. 이 7항목 형식은 본 개정(versioning.md 1.1.0)부터 적용하며, 기존에 3항목(버전/수정일/수정 이유)으로만 작성된 문서는 다음 수정 시점에 7항목으로 갱신한다. 즉시 전수 개정은 강제하지 않는다.
