## 1. 저장 위치 및 설정
- SQLite3 파일은 `database/main.db`에 고정한다.
- DB 연결 전 반드시 디렉토리 존재 여부를 확인하고 없으면 생성한다.
- WAL(Write-Ahead Logging) 모드를 활성화하여 성능을 개선한다.
- 자주 조회되는 컬럼에는 인덱스를 추가한다.

## 2. 스키마 설계 원칙 (동적 확장 구조)
- 모듈별 데이터 테이블은 **사전에 정의하지 않는다.** 모듈을 만들 때마다 필요한 테이블/컬럼을 그때그때 생성하는 것을 기본 운영 방식으로 한다.
- 이를 위해 관리자 페이지는 아래 기능을 제공해야 한다.
  - **스키마 생성**: 테이블 이름, 컬럼(이름/타입/기본값/NULL 허용 여부)을 입력해 새 테이블 생성
  - **스키마 적용**: 작성한 스키마(또는 변경 사항)를 `database/main.db`에 실행
  - **스키마 편집**: 기존 테이블에 컬럼 추가/삭제/타입 변경 (SQLite는 컬럼 변경/삭제 제약이 있으므로 내부적으로 임시 테이블 생성 후 데이터 이관하는 방식 사용)
  - **모듈 연결**: 모듈 생성/편집 화면에서 이 스키마 관리 기능으로 만든 테이블을 해당 모듈에 지정
- 스키마 변경 시 실행될 SQL을 화면에 미리 보여준 뒤 적용하는 것을 권장하되(오조작 방지 목적), 별도 승인자나 결재 절차는 두지 않는다.

## 3. 코어 테이블 (사전 정의, 시스템 운영에 필수)
아래 테이블은 모듈 유무와 관계없이 시스템 운영에 필요하므로 고정 스키마로 둔다. 그 외 데이터 테이블은 모두 2장 방식으로 생성한다.

| 테이블 | 용도 |
|---|---|
| `modules` | 모듈 등록 정보 (name, type, config, tags, metadata) |
| `workflows` | YAML 워크플로우 정의 저장 |
| `scheduled_jobs` | 스케줄러 등록 작업 정보 (`scheduler.md` 2장 참조, `status`/`overlap_policy` 컬럼 포함) |
| `activity_logs` | 실행/종료/에러 등 활동 기록 (source, action, status, message, cpu_usage, memory_usage) |
| `error_logs` | 예외 발생 시 상세 에러 메시지 기록 |

## 4. 설계 원칙
- 코어 테이블의 필수 컬럼은 고정하고, 모듈이 생성하는 테이블은 자유롭게 컬럼을 구성한다.
- 필수 컬럼 누락 시 INSERT를 거부하고, 예외 발생 시 반드시 `error_logs`에 기록한다.
- API 키 등 외부 서비스 연동 정보는 `config.json` 또는 별도 테이블에 저장하되, 별도 암호화는 적용하지 않는다(`security.md` 참조). 다만 `.gitignore`에 포함해 Git 저장소에 커밋되지 않도록 한다.

## 5. 마이그레이션 및 스키마 버전 관리

DB가 커질수록 "언제 어떤 스키마 변경이 적용됐는지" 추적이 필요해진다. 아래를 최소 규칙으로 신설한다.

- 코어 테이블(3장)의 구조 변경은 반드시 이 문서(7장)를 먼저 갱신한 뒤 적용한다.
- 모듈 테이블의 구조 변경(2장 스키마 관리 기능을 통한 변경)은 적용 시점에 `schema_migrations` 코어 테이블에 기록한다. 최소 컬럼: `migration_id`, `module`(모듈 테이블 변경인 경우) 또는 `core`(코어 테이블 변경인 경우), `description`, `applied_sql`, `applied_at`.
- `schema_migrations`는 3장 코어 테이블 목록에 함께 추가한다. 실제 구현 시 이 문서의 코어 테이블 표를 갱신한다.
- 되돌리기(rollback)가 필요한 변경은 적용 전 `applied_sql`과 함께 되돌리는 SQL을 `docs/tips/` 또는 해당 모듈 `docs/`에 남겨둔다. 자동 롤백 기능은 현재 범위에 포함하지 않는다.

## 6. 인덱스, 외래 키, 트랜잭션 원칙

- **인덱스**: `WHERE`/`JOIN`/`ORDER BY`에 자주 사용되는 컬럼에는 인덱스를 추가한다. 인덱스 추가/삭제도 5장 마이그레이션 절차를 따른다.
- **외래 키**: SQLite는 기본적으로 외래 키 제약을 강제하지 않으므로, 연결 시 `PRAGMA foreign_keys = ON`을 명시적으로 설정한다. 모듈 간 테이블 참조가 필요한 경우에만 외래 키를 사용하고, 참조 무결성이 중요하지 않은 로그성 테이블에는 강제하지 않는다.
- **트랜잭션**: 여러 테이블에 걸친 연속 쓰기 작업(예: 워크플로우 실행 결과를 여러 테이블에 나눠 저장)은 트랜잭션으로 묶어 일부만 반영되는 상태를 방지한다. 트랜잭션 실패 시 전체 롤백하고 `error_logs`에 기록한다.

## 7. VACUUM(공간 회수)

- SQLite는 삭제된 데이터의 디스크 공간을 자동으로 회수하지 않는다. 로그성 테이블(`activity_logs`, `error_logs` 등)에서 대량 삭제가 발생한 경우 `VACUUM`을 수동으로 실행해 공간을 회수한다.
- 자동 스케줄링은 현재 범위에 포함하지 않는다. 필요 시 `scheduler.md`(R-005)의 `cron` 방식으로 등록하는 것을 검토하되, 실행 중에는 DB 쓰기가 지연될 수 있으므로 트래픽이 없는 시간대에 수동 실행을 우선한다.

## 8. 백업 및 복구

- 로컬 단독 실행 도구이므로 자동 백업 시스템은 강제하지 않되, 최소한의 절차는 아래와 같다.
- `database/main.db` 및 WAL 관련 파일(`main.db-wal`, `main.db-shm`)을 정기적으로 복사해 별도 위치에 보관하는 것을 권장한다. 자동화 여부는 사용자가 결정한다.
- 스키마 변경(5장) 직전에는 수동으로 백업 파일을 하나 남기는 것을 권장한다. 강제 절차는 아니며, 자동 검증 절차도 두지 않는다(`security.md`의 1인 개발 도구 원칙과 동일).
- 복구 시에는 WAL 파일까지 함께 복원해야 데이터 정합성이 유지된다는 점에 유의한다.
