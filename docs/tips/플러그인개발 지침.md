# 📘 브라우저 플러그인 관리 및 서버 개발 가이드 (1페이지 / 총 15페이지)

---

## 1. 프로젝트 개요

- **목표**  
  본 프로젝트는 **브라우저 플러그인과 서버 간 실시간 통신**을 통해 웹페이지 데이터를 수집·제어하고, 관리자가 플러그인과 모듈을 안정적으로 운영할 수 있는 시스템을 구축하는 것을 목표로 한다.  
  기존 단순 푸시 기반 구조를 확장하여, **사용자 주도형 액션 구조**를 포함한다. 즉, 사용자가 플러그인 UI 버튼을 눌러 서버에 데이터를 전송하거나 특정 모듈을 실행할 수 있다.  
  또한, **모듈별 스크린샷 저장 디렉토리 설정 기능**을 환경 설정에 반영하여 모듈 단위 데이터 관리 효율성을 강화한다.  

- **핵심 기능**  
  - 플러그인 등록 및 승인 절차  
  - 서버와 플러그인 간 WebSocket 실시간 통신  
  - 서버 푸시 기반 모듈 실행 + 사용자 UI 액션 기반 모듈 실행  
  - 플러그인 UI 버튼 → 예: "페이지 전송", "스크린샷 전송", "A프로젝트 실행", "B프로젝트 실행"  
  - 다중 런타임 모듈 지원 → JavaScript, Node.js, Python, Windows 내부 프로그램 실행 가능  
  - 작업 종료 및 알림 시스템  
  - 무한 루프 방지 및 강제 종료  
  - 모듈별 실행 결과 및 기록 관리  
  - 모듈별 스크린샷 저장 디렉토리 환경 설정 지원

## 2. 시스템 주요 특징

- **사용자 주도형 액션 구조**  
  - 플러그인 UI에 기본 메뉴 제공: "페이지 전송", "스크린샷 전송", "A프로젝트 실행", "B프로젝트 실행".  
  - 사용자가 버튼을 누르면 서버에 `action` 메시지 전송 → 서버가 해당 모듈 실행.  
  - 예시 메시지:  
    ```json
    {
      "type": "action",
      "plugin_id": "uuid-1234",
      "action": "A_project",
      "payload": { "screenshot": "base64-data" }
    }
    ```

- **멀티 런타임 모듈 관리**  
  - 모듈 정의 시 `runtime` 필드 추가:  
    - `javascript` → 브라우저 내 Web Worker 실행  
    - `nodejs` → 서버 Node.js 환경 실행  
    - `python` → 서버 Python 환경 실행  
    - `windows_exec` → OS 내부 프로그램 실행  
  - VM/Docker 기반 격리 환경은 사용하지 않으며, 대신 **리소스 사용량 실시간 모니터링**을 통해 안정성을 확보한다.  

- **보안 및 권한 관리**  
  - RBAC(Role-Based Access Control) 기반 권한 세분화.  
  - OS 프로그램 실행은 관리자 승인 필수.  
  - 실행 전 코드 서명 검증 및 **샌드박스 테스트 자동화** 필요.  
  - Windows_exec 모듈 실행 시 추가적인 실행 환경 검증 절차 포함.

## 3. 데이터베이스 구조 개요

- **메인 데이터베이스 (`main.db`)**  
  - 플러그인 등록, 토큰 관리, 모듈 정의, 시스템 로그, 모듈 실행 참조 기록 관리.  
  - 테이블:  
    - `browser_plugins`  
    - `tokens`  
    - `modules` (runtime 필드 포함)  
    - `system_logs`  
    - `module_records`  

- **모듈 전용 데이터베이스 (`module_{id}.db`)**  
  - 모듈별 실행 결과와 수집 데이터 관리.  
  - 테이블:  
    - `collected_data` (HTML, URL, 스크린샷 등)  
    - `execution_logs` (시작/종료, 에러 로그, 실행 환경 정보)  
    - `screenshot_paths` (환경 설정에서 지정된 디렉토리 경로 기록)

## 5. 데이터베이스 구조 상세

- **메인 데이터베이스 (`main.db`)**  
  - 주요 역할: 플러그인 등록, 토큰 관리, 모듈 정의, 시스템 로그, 모듈 실행 참조 기록.  
  - 테이블 구성:  
    - `browser_plugins`: 플러그인 등록 및 상태 관리.  
    - `tokens`: JWT 토큰 및 만료일 관리.  
    - `modules`: 서버에서 관리하는 수행 스크립트 정의 (runtime 필드 포함 → `javascript`, `nodejs`, `python`, `windows_exec`).  
    - `system_logs`: 관리자 이벤트 및 알림 기록.  
    - `module_records`: 모듈별 실행 기록(플러그인 ID, 실행 시간, 종료 상태, 결과 DB 참조).  

- **모듈 전용 데이터베이스 (`module_{id}.db`)**  
  - 모듈별 실행 결과와 수집 데이터 관리.  
  - 테이블 구성:  
    - `collected_data`: 모듈 실행 중 수집된 HTML, URL, 스크린샷 등 저장.  
    - `execution_logs`: 모듈 실행 시작/종료, 에러 로그, 실행 환경(runtime) 기록.  
    - `screenshot_paths`: 모듈별 스크린샷 저장 디렉토리 경로 기록.  

- **DB 최적화 전략**  
  - 모듈별 DB 무한 생성 방지 → 일정 기간 이후 자동 아카이빙 정책을 구체화.  
  - `module_records`와 모듈 DB 간 참조 관계를 외래키·인덱스로 강화하여 추적성 확보.  
  - 실행 환경(runtime) 필드를 추가해 모듈 실행 환경을 명확히 구분.  
  - ELK Stack 연동 시 **실시간 스트리밍 처리**를 고려하여 대규모 확장에 대응.

## 6. MCP 및 Action 메시지 처리 방식

- **지원 메시지 타입**  
  - `register`: 플러그인 등록 요청  
  - `approval`: 서버 승인 응답  
  - `execute`: 서버에서 직접 명령 전달  
  - `push_module`: 서버에서 모듈 선택 후 플러그인에 푸시  
  - `action`: 사용자가 플러그인 UI 버튼 클릭 시 서버에 전송되는 메시지  
  - `result`: 플러그인 실행 결과 반환 (모듈 DB에 기록, 메인 DB에 참조 로그 남김)  
  - `terminate`: 서버에서 강제 종료 명령 → 플러그인 즉시 중단  
  - `refresh`: 토큰 갱신 요청 및 응답  

- **메시지 예시**  
  - **모듈 푸시 (서버 → 플러그인)**:  
    ```json
    {
      "type": "push_module",
      "plugin_id": "uuid-1234",
      "module_id": 5,
      "runtime": "python"
    }
    ```
  - **사용자 액션 (플러그인 → 서버)**:  
    ```json
    {
      "type": "action",
      "plugin_id": "uuid-1234",
      "action": "A_project",
      "payload": { "screenshot": "base64-data" }
    }
    ```
  - **작업 종료 (서버 → 플러그인)**:  
    ```json
    {
      "type": "terminate",
      "plugin_id": "uuid-1234",
      "reason": "manual_stop"
    }
    ```
  - **결과 반환 (플러그인 → 서버)**:  
    ```json
    {
      "type": "result",
      "plugin_id": "uuid-1234",
      "status": "success",
      "payload": {
        "url": "https://example.com/page=1",
        "html": "<html>...</html>"
      }
    }
    ```

## 8. 보안 아키텍처 설계

- **토큰 기반 인증**  
  - 플러그인 등록 시 서버가 JWT 토큰 발급.  
  - 모든 명령 및 데이터 전송은 `plugin_id + token` 검증 필수.  
  - 토큰 만료 시간은 기본 31일 → 운영 환경에서는 7~14일로 단축 권장.  
  - 만료 1일 전 자동 갱신 요청(`refresh`) 처리.  

- **Sandbox 실행 및 검증 절차**  
  - 서버에서 내려보낸 자바스크립트 모듈은 background script 내 Web Worker에서 실행.  
  - DOM 접근, 쿠키/세션 접근 제한 → 보안 강화.  
  - Node.js, Python, Windows 실행 모듈은 격리 환경 대신 **리소스 사용량 실시간 모니터링**을 통해 안정성 확보.  
  - Windows_exec 모듈 실행 시 관리자 승인 외에도 **실행 환경 검증 절차**를 반드시 거침.  
  - 실행 전 코드 서명 검증 및 **샌드박스 테스트 자동화**를 통해 무한 루프나 악성 코드 실행을 사전에 차단.  

- **관리자 인증 및 권한 관리**  
  - 관리 페이지 접근은 관리자 로그인 기반.  
  - RBAC(Role-Based Access Control) 적용: super-admin, operator, auditor, developer 등 세분화.  
  - OS 프로그램 실행은 super-admin 권한에서만 허용.  
  - 각 권한별로 모듈 관리, 로그 조회, 알림 설정 권한을 차등 부여.  

---

## 9. 운영 관리 전략

- **플러그인 모니터링**  
  - 관리 페이지에서 플러그인 소켓 연결 상태, 브라우저 정보, 마지막 활동 시간 표시.  
  - 비정상 종료/연결 끊김 시 상단 알림 바에 Critical Priority 알림 발생.  

- **명령 실행 로그 관리**  
  - 모든 명령 실행 기록을 메인 DB(`system_logs`, `module_records`)에 저장.  
  - 성공/실패 여부, 실행 시간, 결과 데이터 크기 기록.  
  - 모듈별 실행 기록은 `module_records` 테이블에 남겨 모듈 DB와 연결.  

- **데이터 관리**  
  - 수집된 HTML/URL/스크린샷은 모듈별 DB(`module_{id}.db`)에 저장.  
  - 모듈별 스크린샷 저장 디렉토리는 환경 설정에서 지정 가능.  
  - 관리 페이지에서 검색/필터링 가능.  
  - 필요 시 데이터 백업 및 아카이빙.  
  - 장기적으로는 ELK Stack 같은 로그 분석 시스템과 연동하여 성능 및 에러 패턴 시각화.  

- **확장성 고려**  
  - 플러그인 수 증가 시 소켓 연결 관리 최적화 필요.  
  - 메시지 큐(Kafka, RabbitMQ 등) + 로드 밸런싱 + 분산 서버 구조 도입 검토.  
  - 모듈 실행 결과를 이벤트 스트리밍 방식으로 처리하면 대규모 확장에 유리.  
  - 분산 캐시(Redis 등)를 도입하여 성능 향상 및 데이터 접근 속도 개선.

## 11. 모듈 관리 구조

- **모듈 개념**  
  - 모듈은 서버에 저장된 코드 블록으로 특정 작업을 수행하는 단위 기능.  
  - 기존에는 자바스크립트만 지원했으나, 확장된 구조에서는 **Node.js, Python, Windows 내부 프로그램 실행**까지 가능.  
  - 예: "페이징 사이트 수집 모듈", "이미지 다운로드 모듈", "윈도우 프로그램 실행 모듈".  

- **모듈 저장소**  
  - 메인 DB(`main.db`)에 모듈 정의 저장.  
  - 필드 구성: 모듈명, 설명, 버전, 코드(script), 생성일, **runtime 필드**(`javascript`, `nodejs`, `python`, `windows_exec`).  
  - 관리자가 모듈을 등록·수정·삭제 가능.  
  - 모듈 배포 전 자동 테스트 환경을 구축해 무한 루프나 보안 취약점을 사전에 탐지하는 것이 권장됨.  
  - 모듈별 스크린샷 저장 디렉토리 설정을 환경 설정에서 지정하여 실행 시 자동 반영.

## 12. 모듈 전용 데이터베이스

- **모듈별 DB 생성**  
  - 모듈 실행 시 독립된 DB 생성 (예: `module_{id}.db`).  
  - 모듈 단위로 실행 결과와 수집 데이터를 관리.  
  - 테이블 구성:  
    - `collected_data`: 모듈 실행 중 수집된 HTML, URL, 스크린샷 등 저장.  
    - `execution_logs`: 모듈 실행 시작/종료, 에러 로그, 실행 환경(runtime) 기록.  
    - `screenshot_paths`: 모듈별 스크린샷 저장 디렉토리 경로 기록.  

- **서버 기록 관리**  
  - 서버는 모듈 실행 시마다 메인 DB의 `module_records` 테이블에 기록을 남김.  
  - 기록 항목: 플러그인 ID, 모듈 ID, 실행 시작/종료 시간, 종료 상태(success/failed/terminated), 결과 DB 참조 경로, 실행 환경(runtime).  
  - 일정 기간 이후 모듈 DB를 아카이빙하거나 ELK Stack 같은 로그 분석 시스템으로 통합해 관리 효율성을 높임.

## 13. 모듈 푸시 및 액션 실행

- **푸시 메시지**  
  - 관리자가 특정 플러그인을 선택 후 모듈 지정.  
  - 서버가 WebSocket을 통해 `push_module` 메시지 전송.  
  - 해당 플러그인만 모듈을 받아 실행.  

- **사용자 액션 메시지**  
  - 플러그인 UI 버튼 클릭 시 서버에 `action` 메시지 전송.  
  - 예: "페이지 전송", "스크린샷 전송", "A프로젝트 실행".  
  - 서버는 해당 액션에 맞는 모듈을 실행.  

  ```json
  {
    "type": "action",
    "plugin_id": "uuid-1234",
    "action": "A_project",
    "payload": { "screenshot": "base64-data" }
  }
  ```

- **플러그인 실행**  
  - 플러그인은 모듈 ID와 runtime 정보를 받아 서버에서 스크립트를 로드.  
  - 실행 환경:  
    - JavaScript → Web Worker  
    - Node.js → 서버 런타임  
    - Python → 서버 Python 환경  
    - Windows_exec → OS 내부 프로그램 실행  
  - 실행 결과를 `result` 메시지로 서버에 반환 → 모듈 DB에 기록, 동시에 메인 DB에 참조 로그 남김.  
  - 실행 시간, 데이터 크기, 에러율을 자동 집계하여 대시보드에서 시각화 가능.

## 15. 작업 종료 처리

- **작업 종료 트리거**

  - 관리자가 관리자 페이지에서 “작업 종료” 버튼 클릭 시 서버가 `terminate` 메시지를 전송.

- **무한 루프 및 자동 종료**  
  - 서버에서 각 모듈 실행에 타임아웃 설정(예: 5분).  
  - 타임아웃 초과 시 서버가 자동으로 `terminate` 메시지를 전송.  
  - 종료 상태는 `execution_logs`와 `module_records`에 모두 기록.  
  - 추가 개선: CPU 사용률 초과, 메모리 누수, 네트워크 지연, 비정상 패킷 탐지 시 자동 종료/재시작 기능 포함.

## 16. 알림 시스템 설계

- **알림 전달 기술**  
  - WebSocket 또는 Server-Sent Events(SSE)를 사용해 실시간 알림 전달.  
  - 알림은 toast/notification 컴포넌트로 렌더링.

  - Critical Priority: 작업 종료, 강제 종료, 오류 발생 알림 → 최상단 고정.  
  - Warning Priority: 성능 저하, 비정상 연결 → 강조 표시.  
  - Info Priority: 일반 상태 변경, 정보성 알림 → 일정 시간 후 자동 사라짐.  

- **알림 로그 관리**  
  - 알림 로그를 별도 테이블에 저장해 장기적인 분석 가능.  
  - 알림 발생 빈도, 유형, 처리 시간 등을 대시보드에서 시각화.  
  - 알림 로그 테이블에 **처리 결과(acknowledged 여부)** 필드를 추가하여 운영자가 알림을 확인했는지 추적 가능.  
  - Warning/Info 알림은 **사용자 정의 필터링 옵션**을 제공하여 불필요한 알림을 줄임.

## 38. 작업 종료 처리 세부 전략

- **강제 종료**  
  - 관리자가 관리자 페이지에서 “작업 종료” 버튼을 클릭하면 서버가 `terminate` 메시지를 전송.

  - 서버는 종료 이벤트를 모듈 DB와 메인 DB 모두에 기록.

- **자동 종료 조건**  
  - 타임아웃 초과, CPU 사용률 초과, 메모리 누수, 네트워크 지연, 비정상 패킷 탐지 시 자동 종료.

## 39. 알림 시스템 확장 설계

- **알림 전달 방식**

- **알림 우선순위 관리**  
  - Critical Priority: 작업 종료, 강제 종료, 오류 발생 → 최상단 고정, 즉시 외부 메신저 전송.

  - Info Priority: 일반 상태 변경, 정보성 알림 → 일정 시간 후 자동 사라짐, 선택적으로 외부 메신저 전송.  

- **알림 로그 관리**  
  - 알림 로그를 별도 테이블에 저장하여 장기 분석 가능.  
  - 알림 발생 빈도, 유형, 처리 시간, acknowledged 여부 기록.  
  - 사용자 정의 필터링 옵션을 제공하여 불필요한 알림을 줄임.

## 46. 플러그인과 모듈 실행 흐름 심화

- **등록 단계**  
  - 플러그인이 서버에 `register` 메시지를 전송하고, 서버는 승인 후 JWT 토큰을 발급.  
  - 플러그인은 토큰을 사용해 인증된 상태로 대기하며 이후 모든 요청에 토큰을 포함.  

- **모듈 푸시 단계**  
  - 관리자가 특정 플러그인을 선택 후 모듈을 지정.  
  - 서버가 `push_module` 메시지를 전송하여 해당 플러그인만 모듈을 받아 실행.  
  - 실행 환경(runtime)에 따라 Web Worker, Node.js, Python, Windows_exec에서 동작.  

- **사용자 액션 단계**  
  - 사용자가 플러그인 UI 버튼 클릭 → 서버에 `action` 메시지 전송.  
  - 서버는 해당 액션에 맞는 모듈을 실행하고 결과를 모듈 DB 및 메인 DB에 기록.  
  - 모듈별 스크린샷 저장 디렉토리 설정이 반영되어 결과가 지정된 경로에 저장됨.  

- **실행 및 기록 단계**  
  - 플러그인이 모듈 실행 결과를 `result` 메시지로 서버에 반환.  
  - 서버는 결과를 모듈별 DB(`module_{id}.db`)에 저장하고, 메인 DB(`module_records`)에 참조 로그 기록.  
  - 실행 시간, 데이터 크기, 에러율을 자동 집계하여 대시보드에서 시각화.  

- **종료 단계**  
  - 정상 종료: 플러그인이 `result` 메시지 전송 → 서버 기록.  
  - 강제 종료: 관리자가 `terminate` 메시지 전송 → 플러그인 즉시 중단.  
  - 타임아웃 종료: 서버가 자동 `terminate` 메시지 전송.  
  - 모든 종료 이벤트는 모듈 DB와 메인 DB에 기록되며 알림 시스템을 통해 관리자에게 전달.

# ⚙️ 모듈별 스크린샷/저장 경로 환경 설정 구현 가이드

Sujin님 말씀처럼 **서버 관리자 모드에서 로컬 디렉토리를 직접 지정**할 수 있도록 설계하면, 모듈별로 페이지 저장·이미지 저장·동영상 저장 경로를 환경 설정에서 관리할 수 있습니다. 아래는 단계별 구현 예시입니다.

---

## 1. **환경 설정 테이블 설계**
```sql
CREATE TABLE module_settings (
  module_id INTEGER PRIMARY KEY,
  page_dir TEXT,
  image_dir TEXT,
  video_dir TEXT,
  updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```
- `page_dir`: HTML/페이지 저장 경로  
- `image_dir`: 스크린샷 및 이미지 저장 경로  
- `video_dir`: 동영상 저장 경로  

---

## 2. **관리자 페이지 UI 예시**
- 관리자 모드에서 모듈별 환경 설정 메뉴 제공  
- 각 모듈에 대해 **디렉토리 경로 입력 필드** 표시  
- 저장 버튼 클릭 시 DB에 반영  

```html
<form method="POST" action="/admin/module/settings/update">
  <label>페이지 저장 경로</label>
  <input type="text" name="page_dir" value="/data/pages/module_1/">

  <label>이미지 저장 경로</label>
  <input type="text" name="image_dir" value="/data/images/module_1/">

  <label>동영상 저장 경로</label>
  <input type="text" name="video_dir" value="/data/videos/module_1/">

  <button type="submit">저장</button>
</form>
```

---

## 3. **서버 실행 로직 반영**
```javascript
function saveResult(moduleId, type, dataBuffer) {
  const settings = getModuleSettings(moduleId);

  let targetDir;
  switch(type) {
    case "page":
      targetDir = settings.page_dir;
      fs.writeFileSync(`${targetDir}${Date.now()}.html`, dataBuffer);
      break;
    case "image":
      targetDir = settings.image_dir;
      fs.writeFileSync(`${targetDir}${Date.now()}.png`, dataBuffer);
      break;
    case "video":
      targetDir = settings.video_dir;
      fs.writeFileSync(`${targetDir}${Date.now()}.mp4`, dataBuffer);
      break;
  }
}
```
- 모듈 실행 시 DB에서 환경 설정을 불러와 해당 디렉토리에 저장  
- 관리자 모드에서 변경하면 즉시 반영  

---

## 4. **알림 및 로그 반영**
- 저장 경로 변경 시 `system_logs`에 기록  
- 알림 시스템에 “모듈 X 저장 경로 변경됨” 메시지 표시  
- 외부 메신저(Slack/텔레그램/카카오톡)에도 Info Priority 알림 전송 가능  

---

## 5. **개선 포인트**
- 모듈별 저장 경로를 **환경 설정에서 직접 지정 가능**  
- 관리자 모드에서 UI 기반으로 손쉽게 수정  
- 실행 시 자동 반영 → 운영 효율성 강화  
- 로그 및 알림 시스템과 연동하여 변경 내역 추적 가능

# 📑 실제 관리자 시나리오 흐름 (모듈 저장 경로 변경 → 로그 기록 → 알림 발생)

운영 중인 시스템에서 **관리자가 모듈 저장 경로를 변경했을 때** 발생하는 실제 흐름을 단계별로 풀어 설명합니다.

---

## 1. 관리자 액션
- 관리자가 **모듈 상세 페이지 → 환경 설정 메뉴**로 이동  
- `페이지 저장 경로`, `이미지 저장 경로`, `동영상 저장 경로`를 새 디렉토리로 입력  
- “저장” 버튼 클릭  

---

## 2. 서버 처리
- 서버가 변경 요청을 수신  
- `module_settings` 테이블 업데이트:
  ```sql
  UPDATE module_settings
  SET page_dir = '/data/pages/module_A/',
      image_dir = '/data/images/module_A/',
      video_dir = '/data/videos/module_A/',
      updated_at = CURRENT_TIMESTAMP
  WHERE module_id = 1;
  ```
- 변경 내역을 `system_logs`에 기록:
  ```
  [INFO] 모듈 1 저장 경로 변경됨
  page_dir=/data/pages/module_A/
  image_dir=/data/images/module_A/
  video_dir=/data/videos/module_A/
  ```

---

## 3. 실행 반영
- 이후 모듈 실행 시 서버는 DB에서 새 경로를 불러옴  
- 결과 저장 시 지정된 디렉토리에 파일 생성:
  - HTML → `/data/pages/module_A/`  
  - 스크린샷 → `/data/images/module_A/`  
  - 동영상 → `/data/videos/module_A/`  

---

## 4. 알림 시스템 동작
- 알림 바에 Info Priority 메시지 표시:
  ```
  모듈 A 저장 경로 변경됨
  ```
- 외부 메신저(Slack/텔레그램/카카오톡)에 Info 알림 전송:
  ```
  [Info] 모듈 A 저장 경로가 변경되었습니다.
  page_dir=/data/pages/module_A/
  image_dir=/data/images/module_A/
  video_dir=/data/videos/module_A/
  ```

---

## 5. 로그 및 추적
- 알림 로그에 기록:
  - 유형: Info  
  - 메시지: “모듈 A 저장 경로 변경됨”  
  - acknowledged 여부: false (관리자가 확인 시 true로 변경)  
- 실행 로그와 연동되어 이후 저장 결과가 새 경로에 반영됨을 확인 가능  

---

## 📌 요약
- **관리자 액션**: 저장 경로 변경  
- **서버 처리**: DB 업데이트 + 로그 기록  
- **실행 반영**: 새 디렉토리에 결과 저장  
- **알림 시스템**: Info Priority 알림 발생  
- **로그 추적**: 알림 로그 + 실행 로그에 반영

# 📑 실제 관리자 시나리오 흐름 – 시퀀스 다이어그램 (텍스트 버전)

6. **관리자 확인**  
   - 관리자 페이지 알림 바에서 변경 내역 확인  
   - 알림 로그 acknowledged 여부 업데이트

7. **사용자 확인** → 실행 결과 및 알림 확인

# 🔄 브라우저 플러그인 시스템 – 데이터 흐름 다이어그램 (DFD 레벨별 확장)

아래는 앞서 정리한 DFD를 **레벨 0 → 레벨 1**로 확장하여, 데이터 흐름을 더 세부적으로 표현한 구조입니다.

---

## 📍 Level 0 DFD (최상위 흐름)
```
[사용자]
   │
   ▼
[브라우저 플러그인 시스템]
   │
   ▼
[서버 시스템]
   │
   ▼
[데이터베이스 + 알림 시스템]
   │
   ▼
[사용자]
```

- **사용자**: 모듈 실행 요청 입력  
- **브라우저 플러그인 시스템**: 요청 전달 및 결과 표시  
- **서버 시스템**: 모듈 실행 및 데이터 처리  
- **데이터베이스 + 알림 시스템**: 로그 기록 및 알림 발생

```
   │
   ▼
[플러그인 UI] ──> [플러그인 런타임] ──> [API 게이트웨이] ──> [모듈 실행 엔진]
   │                   │                     │                     │
   │                   │                     │                     │
   │                   ▼                     ▼                     ▼
   │              [요청 메시지]          [라우팅 처리]        [실행 결과 생성]
   │                                                           │
   │                                                           ▼
   │                                                [데이터베이스 계층]
   │                                                ├─ module_settings DB
   │                                                ├─ execution_logs DB
   │                                                ├─ system_logs DB
   │                                                └─ alert_logs DB
   │                                                           │
   │                                                           ▼
   │                                                [알림 시스템]
   │                                                ├─ 관리자 페이지 알림 바

   │                                                           │
   ▼                                                           ▼
[사용자] <─────────────────────────────────────────────────────── 결과 + 알림
```

- **Level 0**: 사용자 ↔ 플러그인 ↔ 서버 ↔ DB/알림 ↔ 사용자  
- **Level 1**:

  5. DB → 알림 시스템 (알림 발생)  
  6. 알림 시스템 → 사용자 (알림 표시 + 실행 결과 확인)

## 📍 Level 3 DFD (테이블별 필드 단위 흐름)

```
[모듈 실행 엔진] → SELECT page_dir, image_dir, video_dir FROM module_settings WHERE module_id=1
```

아래는 **브라우저 플러그인 시스템의 데이터베이스 구조**를 **ERD 텍스트 버전**으로 정리한 것입니다. 각 테이블과 컬럼, 그리고 관계(FK/PK)를 포함합니다.

---

## 📍 테이블 구조 및 관계

### 1. **module_settings**
- **컬럼**
  - `module_id` (PK)
  - `page_dir`
  - `image_dir`
  - `video_dir`
  - `updated_at`
- **관계**
  - `module_id` → execution_logs / alert_logs 에서 참조 (FK)

---

### 2. **execution_logs**
- **컬럼**
  - `log_id` (PK)
  - `module_id` (FK → module_settings.module_id)
  - `status` (SUCCESS/FAILURE)
  - `output_path`
  - `execution_time`
  - `created_at`
- **관계**
  - `module_id` → module_settings 참조

### 3. **system_logs**
- **컬럼**
  - `log_id` (PK)
  - `event_type` (EXECUTION/ERROR/TERMINATION)
  - `message`
  - `timestamp`
- **관계**
  - 독립적 로그 테이블 (다른 테이블과 직접 FK 관계 없음)
  - 관리자 감사 및 모니터링 용도

### 4. **alert_logs**
- **컬럼**
  - `alert_id` (PK)
  - `module_id` (FK → module_settings.module_id)
  - `priority` (Critical/Warning/Info)
  - `message`
  - `acknowledged` (TRUE/FALSE)
  - `created_at`
- **관계**
  - `module_id` → module_settings 참조
  - 알림 시스템과 연결되어 관리자 페이지 및 외부 메신저로 전달

---

## 📍 ERD 텍스트 다이어그램

```
module_settings (PK: module_id)
   ├─ page_dir
   ├─ image_dir
   ├─ video_dir
   └─ updated_at
        │
        │ 1:N
        ▼
execution_logs (PK: log_id, FK: module_id)
   ├─ status
   ├─ output_path
   ├─ execution_time
   └─ created_at

module_settings (PK: module_id)
        │
        │ 1:N
        ▼
alert_logs (PK: alert_id, FK: module_id)
   ├─ priority
   ├─ message
   ├─ acknowledged
   └─ created_at

system_logs (PK: log_id)
   ├─ event_type
   ├─ message
   └─ timestamp
```

- **module_settings**는 중심 테이블로, 모듈별 저장 경로 관리

- 알림 시스템은 **alert_logs**를 기반으로 관리자 페이지와 외부 메신저에 메시지를 전달  

# 📊 브라우저 플러그인 시스템 – ERD 정규화 관점 (NF1 ~ NF3)

이제 앞서 정리한 ERD를 **정규화(Normalization)** 관점에서 풀어내어, 데이터 중복 제거와 무결성 확보 방안을 설명합니다.

---

## 1️⃣ **제1정규형 (NF1)**
- **조건**: 모든 속성은 원자값(Atomic Value)이어야 함. 반복 그룹이나 다중 값 컬럼이 없어야 함.
- **적용**
  - `module_settings` 테이블의 `page_dir`, `image_dir`, `video_dir`는 각각 독립된 컬럼으로 원자값을 가짐 → NF1 만족
  - `execution_logs`의 `status`, `output_path`, `execution_time`도 단일 값 → NF1 만족
  - `alert_logs`의 `acknowledged`는 Boolean 값으로 원자적 → NF1 만족
- **효과**
  - 데이터가 중복 없이 단일 값으로 저장되어 검색과 갱신이 용이

---

## 2️⃣ **제2정규형 (NF2)**
- **조건**: 부분 함수 종속 제거. 기본키의 일부에만 종속된 속성이 없어야 함.
- **적용**
  - `execution_logs`의 PK는 `log_id`. 모든 속성(`module_id`, `status`, `output_path`, `execution_time`)은 `log_id` 전체에 종속 → NF2 만족
  - `alert_logs`의 PK는 `alert_id`. 모든 속성(`module_id`, `priority`, `message`, `acknowledged`)은 `alert_id` 전체에 종속 → NF2 만족
  - `system_logs`의 PK는 `log_id`. 모든 속성은 `log_id` 전체에 종속 → NF2 만족
- **효과**
  - 부분 종속 제거로 데이터 무결성 확보, 중복 최소화

---

## 3️⃣ **제3정규형 (NF3)**
- **조건**: 이행적 종속 제거. 기본키가 아닌 다른 속성에 종속된 속성이 없어야 함.
- **적용**
  - `execution_logs`에서 `module_id`는 FK로 `module_settings` 참조. `output_path`는 `module_id`에 종속되지 않고 실행 결과에만 종속 → NF3 만족
  - `alert_logs`에서 `priority`, `message`, `acknowledged`는 `alert_id`에 직접 종속 → NF3 만족
  - `system_logs`에서 `event_type`, `message`는 `log_id`에 직접 종속 → NF3 만족
- **효과**
  - 이행적 종속 제거로 데이터 중복 방지 및 무결성 강화
  - 예: 알림 메시지(`message`)가 `priority`에 종속되지 않고 `alert_id`에만 종속되므로 NF3 충족

---

## 📌 요약
- **NF1**: 모든 컬럼은 원자값으로 구성 → 반복 그룹 제거  
- **NF2**: 부분 종속 제거 → PK 전체에만 종속  
- **NF3**: 이행적 종속 제거 → PK에 직접 종속, 다른 속성에 종속되지 않음  
- 결과적으로, 이 ERD는 **NF3까지 충족**하여 데이터 중복을 최소화하고 무결성을 확보한 구조임  

---

# 🗄 브라우저 플러그인 시스템 – SQL 테이블 정의 예시 (DDL)

아래는 앞서 정리한 ERD와 정규화(NF1~NF3) 관점을 기반으로 작성한 **실제 SQL 테이블 정의 예시**입니다. 각 테이블은 PK/FK 제약 조건을 포함하여 무결성을 확보합니다.

---

## 1️⃣ **module_settings**
```sql
CREATE TABLE module_settings (
    module_id      INT PRIMARY KEY,
    page_dir       VARCHAR(255) NOT NULL,
    image_dir      VARCHAR(255) NOT NULL,
    video_dir      VARCHAR(255) NOT NULL,
    updated_at     TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```
- 모듈별 저장 경로 관리 테이블  
- `module_id`는 다른 테이블에서 FK로 참조됨  

---

## 2️⃣ **execution_logs**
```sql
CREATE TABLE execution_logs (
    log_id         BIGINT PRIMARY KEY AUTO_INCREMENT,
    module_id      INT NOT NULL,
    status         VARCHAR(20) CHECK (status IN ('SUCCESS','FAILURE')),
    output_path    VARCHAR(255),
    execution_time DECIMAL(6,2),
    created_at     TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (module_id) REFERENCES module_settings(module_id)
        ON UPDATE CASCADE
        ON DELETE CASCADE
);
```
- 실행 결과 기록 테이블  
- `status`는 성공/실패만 허용  
- `module_id`는 `module_settings` 참조  

---

## 3️⃣ **system_logs**
```sql
CREATE TABLE system_logs (
    log_id     BIGINT PRIMARY KEY AUTO_INCREMENT,
    event_type VARCHAR(30) CHECK (event_type IN ('EXECUTION','ERROR','TERMINATION')),
    message    TEXT NOT NULL,
    timestamp  TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```
- 시스템 이벤트 기록 테이블  
- 독립적이며 다른 테이블과 직접 FK 관계 없음  

---

## 4️⃣ **alert_logs**
```sql
CREATE TABLE alert_logs (
    alert_id     BIGINT PRIMARY KEY AUTO_INCREMENT,
    module_id    INT NOT NULL,
    priority     VARCHAR(20) CHECK (priority IN ('Critical','Warning','Info')),
    message      TEXT NOT NULL,
    acknowledged BOOLEAN DEFAULT FALSE,
    created_at   TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (module_id) REFERENCES module_settings(module_id)
        ON UPDATE CASCADE
        ON DELETE CASCADE
);
```
- 알림 발생 내역 기록 테이블  
- `acknowledged`는 관리자 확인 여부 표시  
- `priority`는 Critical/Warning/Info만 허용

## 📌 무결성 확보 방안
- **PK 제약 조건**: 각 테이블의 고유 식별자(`module_id`, `log_id`, `alert_id`)로 중복 제거  
- **FK 제약 조건**: `execution_logs`와 `alert_logs`는 `module_settings`를 참조하여 모듈 무결성 확보  
- **CHECK 제약 조건**: `status`, `event_type`, `priority` 값의 유효성 보장  
- **CASCADE 옵션**: 모듈 삭제 시 관련 로그와 알림도 함께 삭제 → 데이터 일관성 유지

# 🔄 A프로젝트 실행 흐름 – 트랜잭션 단위 시뮬레이션 (ACID 관점)

이제 **트랜잭션 단위 시뮬레이션**을 **ACID 특성** 관점에서 풀어내어, 데이터베이스가 어떻게 원자성·일관성·격리성·지속성을 보장하는지 설명합니다.

---

## 1️⃣ **원자성 (Atomicity)**
- **정의**: 트랜잭션 내 모든 작업은 전부 수행되거나 전혀 수행되지 않아야 함.
- **적용**
  - `execution_logs`, `system_logs`, `alert_logs`에 대한 INSERT가 모두 성공해야만 `COMMIT` 수행.
  - 실행 중 하나라도 실패하면 `ROLLBACK`으로 전체 취소.
- **보장**
  - 프로젝트 A 실행 중 오류 발생 시, 실행 결과·로그·알림이 부분적으로만 저장되는 상황을 방지.

---

## 2️⃣ **일관성 (Consistency)**
- **정의**: 트랜잭션 전후로 데이터베이스는 항상 유효한 상태를 유지해야 함.
- **적용**
  - `module_id`는 반드시 `module_settings`에 존재해야 함 (FK 제약 조건).
  - `status`는 `SUCCESS` 또는 `FAILURE`만 허용 (CHECK 제약 조건).
  - `priority`는 `Critical`, `Warning`, `Info`만 허용.
- **보장**
  - 잘못된 모듈 ID나 잘못된 상태 값이 DB에 들어가는 것을 방지.

---

## 3️⃣ **격리성 (Isolation)**
- **정의**: 동시에 실행되는 트랜잭션이 서로 간섭하지 않아야 함.
- **적용**
  - 프로젝트 A 실행 트랜잭션은 다른 프로젝트 실행 트랜잭션과 독립적으로 처리.
  - DB 격리 수준(예: READ COMMITTED, SERIALIZABLE)에 따라 동시 실행 시 충돌 방지.
- **보장**
  - 여러 사용자가 동시에 실행 요청을 해도, 각 실행 결과와 로그가 서로 뒤섞이지 않음.

---

## 4️⃣ **지속성 (Durability)**
- **정의**: 커밋된 트랜잭션의 결과는 영구적으로 저장되어야 함.
- **적용**
  - `COMMIT` 후 실행 결과와 로그는 디스크에 기록되어 시스템 장애 발생 시에도 유지.
  - 알림 로그(`alert_logs`)도 커밋 이후에는 관리자 페이지와 외부 메신저에 반영됨.
- **보장**
  - 서버 다운이나 장애가 발생해도, 커밋된 실행 결과는 복구 가능.

---

## 📌 A프로젝트 실행 트랜잭션 흐름 (ACID 관점)
```
BEGIN TRANSACTION
   → INSERT execution_logs
   → INSERT system_logs
   → INSERT alert_logs
IF 모든 SQL 성공 THEN COMMIT
ELSE ROLLBACK
```

- **Atomicity**: 전부 성공 시 커밋, 실패 시 롤백  
- **Consistency**: FK/CK 제약 조건으로 데이터 무결성 유지  
- **Isolation**: 동시 실행 시에도 독립적 처리  
- **Durability**: 커밋된 결과는 영구 저장

# ⚠️ A프로젝트 실행 – 장애 발생 시 복구 시나리오 (ACID 관점 확장)

이번에는 **서버 다운 등 장애 발생 상황**에서 트랜잭션과 로그, 알림 시스템이 어떻게 동작하며 복구되는지까지 설명합니다.

---

## 🕒 장애 발생 시나리오

### 1. 실행 중 서버 다운 발생
- 트랜잭션이 `BEGIN TRANSACTION` 상태에서 SQL 실행 중 서버 다운  
- 아직 `COMMIT`이 수행되지 않았으므로 DB는 **롤백 상태**로 유지  

```
[DB] 트랜잭션 미완료 → 자동 ROLLBACK 수행
```

---

### 2. DB 상태
- **execution_logs**: 실행 결과 INSERT 미반영  
- **system_logs**: 이벤트 기록 미반영  
- **alert_logs**: 알림 발생 내역 미반영  
- DB는 **일관성(Consistency)**을 유지하며, 잘못된 데이터가 저장되지 않음  

---

### 3. 알림 시스템 반응
- 트랜잭션 실패 감지 → **Critical 알림 발생**  
- 관리자 페이지 및 외부 메신저에 장애 알림 전송  

```
[ALERT_BAR] Critical: 프로젝트 A 실행 실패 – DB 롤백 수행
[Slack] [Critical] 프로젝트 A 실행 실패 – 서버 다운 감지, 트랜잭션 롤백 완료
```

---

### 4. 복구 과정
- 서버 재시작 후, 트랜잭션 로그를 기반으로 복구 수행  
- DBMS는 **Redo/Undo 로그**를 활용하여 상태 복원  
  - **Undo 로그**: 실패한 트랜잭션을 취소  
  - **Redo 로그**: 커밋된 트랜잭션을 재적용  

```
[DB RECOVERY] Undo: 미완료 트랜잭션 취소
[DB RECOVERY] Redo: 커밋된 트랜잭션 재적용
```

---

### 5. 사용자 확인
- 플러그인 UI에 실행 실패 메시지 표시  
- 관리자 알림을 통해 장애 상황 인지  
- 복구 후 재실행 가능  

```
[PLUGIN_UI] 프로젝트 A 실행 실패 – 관리자에게 알림 전송됨
```

---

## 📌 ACID 특성 보장 (장애 발생 시)
- **Atomicity (원자성)**: 실패 시 전체 롤백 → 부분 저장 없음  
- **Consistency (일관성)**: FK/CK 제약 조건 유지 → 잘못된 데이터 없음  
- **Isolation (격리성)**: 다른 트랜잭션은 독립적으로 정상 처리  
- **Durability (지속성)**: 커밋된 트랜잭션은 Redo 로그로 복구 가능

```
[Slack] [Info] 프로젝트 A 스크린샷 업로드 완료 – /data/images/project_A/screenshot_20260727.png
```

## 🕒 Step 7. 사용자 확인
- 플러그인 UI에 스크린샷 업로드 성공 메시지 표시

- 서버 API 게이트웨이에 종료 요청 전송


아래는 **프로젝트 실행 중 강제 종료 발생 시** 실제 SQL 로그 예시와 알림 메시지를 병합한 상세 데이터 흐름입니다. 트랜잭션 취소, 로그 기록, 알림 발생까지 모두 포함합니다.

---

## 🕒 Step 1. 사용자 액션
```
[PLUGIN_UI] 사용자 강제 종료 요청 발생
```

---

## 🕒 Step 2. 플러그인 런타임 처리
```
[PLUGIN_RUNTIME] 종료 요청 메시지 전송 → { "project": "A", "action": "force_terminate" }
```

---

## 🕒 Step 3. 서버 API 게이트웨이
```
[API_GATEWAY] 프로젝트 A 강제 종료 요청 전달 → module_id=101
```

---

## 🕒 Step 4. 모듈 실행 엔진 – 트랜잭션 취소
```sql
-- 실행 중 트랜잭션 취소
ROLLBACK;
```

- 실행 중이던 SQL 작업은 모두 취소됨  
- 이후 종료 이벤트 및 알림 로그 기록  

```sql
-- 시스템 로그 기록
INSERT INTO system_logs (event_type, message, timestamp)
VALUES ('TERMINATION', '프로젝트 A 강제 종료 수행', CURRENT_TIMESTAMP);

-- 알림 로그 기록
INSERT INTO alert_logs (module_id, priority, message, acknowledged, created_at)
VALUES (101, 'Warning', '프로젝트 A 실행이 강제 종료되었습니다.', FALSE, CURRENT_TIMESTAMP);
```

---

## 🕒 Step 5. DB 반영
```
[DB] execution_logs → 롤백 처리 (실행 결과 미반영)
[DB] system_logs → TERMINATION 이벤트 기록 완료
[DB] alert_logs → Warning 알림 발생 기록 완료
```

---

## 🕒 Step 6. 알림 시스템
```
[ALERT_BAR] Warning: 프로젝트 A 실행 강제 종료
[Slack] [Warning] 프로젝트 A 실행이 강제 종료되었습니다.
[Telegram] Warning: 프로젝트 A 실행 강제 종료
```

---

## 🕒 Step 7. 사용자 확인
```
[PLUGIN_UI] 프로젝트 A 실행이 강제 종료되었습니다.
```

---

## 📌 데이터 흐름 요약
1. **사용자 요청** → 강제 종료 버튼 클릭  
2. **플러그인 런타임** → 종료 요청 메시지 생성 후 서버 전달  
3. **서버 API 게이트웨이** → 모듈 실행 엔진으로 라우팅  
4. **모듈 실행 엔진** → 트랜잭션 ROLLBACK 수행, 종료 이벤트 및 알림 로그 기록  
5. **DB 계층** → 실행 로그 취소, 종료 이벤트 기록, 알림 로그 기록  
6. **알림 시스템** → 관리자 페이지 + 외부 메신저에 Warning 알림 발생  
7. **사용자 확인** → 강제 종료 메시지 확인

# ⏱️ 자동 종료(타임아웃 발생) 시 상세 데이터 흐름

이번에는 **프로젝트 실행 중 타임아웃이 발생하여 자동 종료되는 경우**의 데이터 흐름을 단계별로 정리합니다. 강제 종료와 달리, 시스템이 **시간 제한을 감지**하여 종료 처리와 로그·알림을 남깁니다.

---

## 🕒 Step 1. 실행 중 타임아웃 발생
- 모듈 실행 엔진이 설정된 제한 시간 초과 감지  
- 자동 종료 프로세스 시작  

```
[MODULE_ENGINE] 타임아웃 발생 → 자동 종료 프로세스 시작
```

---

## 🕒 Step 2. 트랜잭션 처리
- 실행 중 트랜잭션은 **ROLLBACK** 수행  
- 실행 결과는 DB에 반영되지 않음  

```sql
ROLLBACK;
```

---

## 🕒 Step 3. 로그 기록
- 시스템 로그에 자동 종료 이벤트 기록  
- 알림 로그에 Warning 알림 기록  

```sql
-- 시스템 로그 기록
INSERT INTO system_logs (event_type, message, timestamp)
VALUES ('TERMINATION', '프로젝트 A 자동 종료(타임아웃 발생)', CURRENT_TIMESTAMP);

-- 알림 로그 기록
INSERT INTO alert_logs (module_id, priority, message, acknowledged, created_at)
VALUES (101, 'Warning', '프로젝트 A 실행이 타임아웃으로 자동 종료되었습니다.', FALSE, CURRENT_TIMESTAMP);
```

---

## 🕒 Step 4. DB 반영
```
[DB] execution_logs → 롤백 처리 (실행 결과 미반영)
[DB] system_logs → TERMINATION 이벤트 기록 완료
[DB] alert_logs → Warning 알림 발생 기록 완료
```

---

## 🕒 Step 5. 알림 시스템
- 관리자 페이지 알림 바에 Warning 메시지 표시  
- 외부 메신저(Slack/텔레그램/카카오톡) 알림 전송  

```
[ALERT_BAR] Warning: 프로젝트 A 실행 자동 종료(타임아웃)
[Slack] [Warning] 프로젝트 A 실행이 타임아웃으로 자동 종료되었습니다.
```

---

## 🕒 Step 6. 사용자 확인
- 플러그인 UI에 자동 종료 메시지 표시  
- 실행 결과는 저장되지 않음  

```
[PLUGIN_UI] 프로젝트 A 실행이 타임아웃으로 자동 종료되었습니다.
```

---

## 📌 데이터 흐름 요약
1. **타임아웃 감지** → 모듈 실행 엔진이 제한 시간 초과 확인  
2. **트랜잭션 처리** → ROLLBACK 수행, 실행 결과 취소  
3. **로그 기록** → `system_logs`에 자동 종료 이벤트 기록  
4. **알림 로그** → `alert_logs`에 Warning 알림 기록  
5. **알림 시스템** → 관리자 페이지 + 외부 메신저에 Warning 알림 발생  
6. **사용자 확인** → 자동 종료 메시지 확인

# 🔄 자동 재시작(조건 충족 시) – 상세 데이터 흐름

이번에는 **프로젝트 실행 중 자동 종료(타임아웃 등) 이후 조건 충족 시 자동 재시작**되는 경우의 데이터 흐름을 단계별로 정리합니다. 시스템이 종료를 감지하고, 재시작 조건을 확인한 뒤 다시 실행을 이어가는 과정입니다.

---

## 🕒 Step 1. 타임아웃 발생 → 자동 종료
- 모듈 실행 엔진이 제한 시간 초과 감지  
- 트랜잭션 ROLLBACK 수행  
- 종료 이벤트 및 알림 로그 기록  

```sql
ROLLBACK;

INSERT INTO system_logs (event_type, message, timestamp)
VALUES ('TERMINATION', '프로젝트 A 자동 종료(타임아웃 발생)', CURRENT_TIMESTAMP);

INSERT INTO alert_logs (module_id, priority, message, acknowledged, created_at)
VALUES (101, 'Warning', '프로젝트 A 실행이 타임아웃으로 자동 종료되었습니다.', FALSE, CURRENT_TIMESTAMP);
```

---

## 🕒 Step 2. 재시작 조건 확인
- 모듈 실행 엔진이 **자동 재시작 조건**을 검사  
  - 예: 네트워크 연결 복구, 리소스 사용률 정상화, 관리자 정책 허용  
- 조건 충족 시 자동 재시작 프로세스 시작  

```
[MODULE_ENGINE] 조건 충족 확인 → 자동 재시작 프로세스 시작
```

---

## 🕒 Step 3. 트랜잭션 재시작
- 새로운 트랜잭션 시작  
- 실행 로그 및 시스템 로그 기록  

```sql
BEGIN TRANSACTION;

INSERT INTO execution_logs (module_id, status, output_path, execution_time, created_at)
VALUES (101, 'SUCCESS', '/data/pages/project_A/restart_20260727.html', 5.2, CURRENT_TIMESTAMP);

INSERT INTO system_logs (event_type, message, timestamp)
VALUES ('RESTART', '프로젝트 A 자동 재시작 성공', CURRENT_TIMESTAMP);

INSERT INTO alert_logs (module_id, priority, message, acknowledged, created_at)
VALUES (101, 'Info', '프로젝트 A 실행이 자동 재시작되었습니다.', FALSE, CURRENT_TIMESTAMP);

COMMIT;
```

---

## 🕒 Step 4. DB 반영
```
[DB] execution_logs → 재시작 실행 결과 기록 완료
[DB] system_logs → RESTART 이벤트 기록 완료
[DB] alert_logs → Info 알림 발생 기록 완료
```

---

## 🕒 Step 5. 알림 시스템
- 관리자 페이지 알림 바에 Info 메시지 표시  
- 외부 메신저(Slack/텔레그램/카카오톡) 알림 전송  

```
[ALERT_BAR] Info: 프로젝트 A 자동 재시작 성공
[Slack] [Info] 프로젝트 A 실행이 자동 재시작되었습니다.
```

---

## 🕒 Step 6. 사용자 확인
- 플러그인 UI에 자동 재시작 성공 메시지 표시  
- 새로운 실행 결과 경로 확인 가능  

```
[PLUGIN_UI] 프로젝트 A 실행이 자동 재시작되었습니다.
HTML=/data/pages/project_A/restart_20260727.html
```

---

## 📌 데이터 흐름 요약
1. **타임아웃 발생** → 자동 종료 및 Warning 알림 기록  
2. **조건 확인** → 네트워크/리소스/정책 등 재시작 조건 충족 여부 검사  
3. **트랜잭션 재시작** → 새로운 실행 로그, 시스템 로그, 알림 로그 기록

5. **알림 시스템** → Info 알림 발생 (관리자 페이지 + 외부 메신저)  
6. **사용자 확인** → 자동 재시작 성공 메시지 및 결과 확인

# 🔄 자동 재시작(조건 충족 시) – SQL 로그 + 알림 메시지 병합 시뮬레이션

아래는 **프로젝트 실행 중 타임아웃 종료 후 조건 충족 시 자동 재시작되는 경우** 실제 SQL 로그 예시와 알림 메시지를 병합한 상세 데이터 흐름입니다.

## 🕒 Step 1. 타임아웃 발생 → 자동 종료
```sql
ROLLBACK;

INSERT INTO system_logs (event_type, message, timestamp)

```

# 🔐 ACID 관점에서 외부 알림까지 포함한 무결성 보장 시나리오

이번에는 **외부 알림 시스템 연동**까지 고려하여, **알림 전송 실패 시 재시도·로그 보존·사용자 통지**가 어떻게 이루어지는지 **ACID 특성 관점**에서 확장된 시나리오를 설명합니다.

---

## 1️⃣ **원자성 (Atomicity)**
- **정의**: 트랜잭션 내 모든 작업은 전부 수행되거나 전혀 수행되지 않아야 함.
- **적용**
  - 이벤트 발생 시 `system_logs`, `alert_logs` 기록은 반드시 함께 수행.
  - 외부 알림 전송은 별도 프로세스로 처리되지만, **내부 로그 기록은 항상 원자적으로 보장**.
- **보장**
  - 알림 전송 실패해도 DB 로그는 남아 있어, 재시도 프로세스가 정확히 어떤 알림을 다시 보낼지 추적 가능.

---

## 2️⃣ **일관성 (Consistency)**
- **정의**: 트랜잭션 전후로 데이터베이스는 항상 유효한 상태를 유지해야 함.
- **적용**
  - 알림 로그(`alert_logs`)는 전송 상태 필드를 포함 (`status = PENDING / SENT / FAILED`).
  - 실패 시 `FAILED` 상태로 기록 → 재시도 시 `RETRYING → SENT`로 업데이트.
- **보장**
  - 알림 상태가 DB에 정확히 반영되어, 외부 알림 시스템과 내부 로그 간 불일치 방지.

---

## 3️⃣ **격리성 (Isolation)**
- **정의**: 동시에 실행되는 트랜잭션이 서로 간섭하지 않아야 함.
- **적용**
  - 여러 알림이 동시에 발생해도, 각 알림 로그는 독립적으로 기록 및 전송.
  - 재시도 큐(Queue)는 개별 알림 단위로 처리 → 다른 알림에 영향 없음.
- **보장**
  - 특정 알림 전송 실패가 다른 알림 전송 성공에 영향을 주지 않음.

---

## 4️⃣ **지속성 (Durability)**
- **정의**: 커밋된 트랜잭션의 결과는 영구적으로 저장되어야 함.
- **적용**
  - 알림 로그는 DB에 영구 저장 → 서버 다운 후에도 복구 가능.
  - 실패한 알림은 `FAILED` 상태로 남아 있어, 재시도 프로세스가 장애 복구 후 다시 실행.
- **보장**
  - 알림 전송 실패 후 서버 재시작 시에도, DB 로그를 기반으로 재전송 가능.

---

## 🕒 실제 SQL 로그 예시 (알림 실패 → 재시도 → 성공)

```sql
-- 알림 최초 기록
INSERT INTO alert_logs (module_id, priority, message, status, created_at)
VALUES (101, 'Info', '프로젝트 A 실행이 자동 재시작되었습니다.', 'PENDING', CURRENT_TIMESTAMP);

-- 외부 알림 전송 실패 시
UPDATE alert_logs
SET status = 'FAILED', updated_at = CURRENT_TIMESTAMP
WHERE module_id = 101 AND message LIKE '%자동 재시작%';

-- 재시도 프로세스 실행
UPDATE alert_logs
SET status = 'RETRYING', updated_at = CURRENT_TIMESTAMP
WHERE module_id = 101 AND status = 'FAILED';

-- 재전송 성공 시
UPDATE alert_logs
SET status = 'SENT', updated_at = CURRENT_TIMESTAMP
WHERE module_id = 101 AND status = 'RETRYING';
```

---

## 📢 알림 메시지 흐름
- **실패 시**
  ```
  [ALERT_BAR] Warning: 외부 알림 전송 실패 – 재시도 예정
  [Slack] [Error] 프로젝트 A 알림 전송 실패
  ```
- **재시도 후 성공 시**
  ```
  [ALERT_BAR] Info: 프로젝트 A 알림 재전송 성공
  [Slack] [Info] 프로젝트 A 실행이 자동 재시작되었습니다.
  ```

---

## 📌 전체 시나리오 요약
1. **이벤트 발생** → 내부 로그 기록 (`system_logs`, `alert_logs`)  
2. **외부 알림 전송 시도** → 실패 시 `FAILED` 상태 기록  
3. **재시도 프로세스** → 큐 기반으로 실패 알림 재전송  
4. **성공 시** → `SENT` 상태 업데이트, 알림 정상 반영  
5. **사용자 통지** → 관리자 페이지 + 외부 알림 시스템에 실패/재시도/성공 상태 표시  

---

# 📑 외부 알림 연동 – 실패·재시도·성공 시퀀스 다이어그램 (텍스트 버전)

아래는 **DB → 알림 브로커 → 외부 시스템 → 사용자**까지의 흐름을, 알림 전송 실패 → 재시도 → 성공까지 포함해 시퀀스 다이어그램 텍스트로 정리한 구조입니다.

---

```
모듈 실행 엔진        DB 계층                  알림 브로커              외부 알림 시스템(Slack/Telegram/Email)        사용자
     │                   │                        │                                  │                                  │
     │--- 이벤트 발생 --->│                        │                                  │                                  │
     │                   │--- system_logs 기록 --->│                                  │                                  │
     │                   │--- alert_logs 기록 ---->│                                  │                                  │
     │                   │                        │--- 알림 로그 읽기 ---------------->│                                  │
     │                   │                        │--- 메시지 변환 ------------------->│                                  │
     │                   │                        │                                  │--- 알림 전송 시도 ---------------->│
     │                   │                        │                                  │--- 전송 실패 --------------------->│
     │                   │                        │<-- 실패 상태 반영 ----------------│                                  │
     │                   │--- alert_logs 업데이트 (FAILED) --------------------------->│                                  │
     │                   │                        │--- 재시도 큐 등록 ---------------->│                                  │
     │                   │                        │--- 재시도 실행 ------------------->│                                  │
     │                   │                        │                                  │--- 알림 재전송 ------------------>│
     │                   │                        │                                  │--- 전송 성공 -------------------->│
     │                   │                        │<-- 성공 상태 반영 ----------------│                                  │
     │                   │--- alert_logs 업데이트 (SENT) ----------------------------->│                                  │
     │                   │                        │                                  │                                  │--- 알림 확인
     │                   │                        │                                  │                                  │<-- 알림 메시지 수신
```

---

## 📌 단계별 설명
1. **모듈 실행 엔진** → 이벤트 발생 후 DB에 로그 기록 (`system_logs`, `alert_logs`).  
2. **알림 브로커** → DB에서 알림 로그 읽고 외부 메시지로 변환.  
3. **외부 알림 시스템** → Slack/Telegram/Email API 호출로 알림 전송 시도.  
4. **실패 시** → DB에 `FAILED` 상태 기록, 알림 브로커가 재시도 큐에 등록.  
5. **재시도 실행** → 알림 브로커가 다시 외부 시스템에 전송.  
6. **성공 시** → DB에 `SENT` 상태 업데이트.  
7. **사용자 확인** → 관리자 페이지 알림 바 + 외부 알림 시스템에서 메시지 확인.  

---

## 📌 알림 메시지 예시
- **실패 시**
  ```
  [ALERT_BAR] Warning: 외부 알림 전송 실패 – 재시도 예정
  [Slack] [Error] 프로젝트 A 알림 전송 실패
  ```
- **재시도 후 성공 시**
  ```
  [ALERT_BAR] Info: 프로젝트 A 알림 재전송 성공
  [Slack] [Info] 프로젝트 A 실행이 자동 재시작되었습니다.
  [Telegram] Info: 프로젝트 A 실행 자동 재시작 성공
  ```

# 📑 외부 알림 연동 – 실패·재시도·성공 단계별 SQL 로그 + 알림 메시지 병합 시나리오

아래는 **알림 전송 실패 → 재시도 → 성공**까지의 과정을 실제 SQL 로그 예시와 알림 메시지를 병합해 정리한 상세 흐름입니다.

---

## 🕒 Step 1. 알림 최초 기록 (PENDING 상태)
```sql
INSERT INTO alert_logs (module_id, priority, message, status, created_at)
VALUES (101, 'Info', '프로젝트 A 실행이 자동 재시작되었습니다.', 'PENDING', CURRENT_TIMESTAMP);
```

**알림 메시지**
```
[ALERT_BAR] Info: 알림 전송 준비 중
```

---

## 🕒 Step 2. 외부 알림 전송 실패 (FAILED 상태)
```sql
UPDATE alert_logs
SET status = 'FAILED', updated_at = CURRENT_TIMESTAMP
WHERE module_id = 101 AND message LIKE '%자동 재시작%';
```

**알림 메시지**
```
[ALERT_BAR] Warning: 외부 알림 전송 실패 – 재시도 예정
[Slack] [Error] 프로젝트 A 알림 전송 실패
[Telegram] Error: 프로젝트 A 알림 전송 실패
```

---

## 🕒 Step 3. 재시도 프로세스 실행 (RETRYING 상태)
```sql
UPDATE alert_logs
SET status = 'RETRYING', updated_at = CURRENT_TIMESTAMP
WHERE module_id = 101 AND status = 'FAILED';
```

**알림 메시지**
```
[ALERT_BAR] Info: 알림 재전송 시도 중…
```

---

## 🕒 Step 4. 재전송 성공 (SENT 상태)
```sql
UPDATE alert_logs
SET status = 'SENT', updated_at = CURRENT_TIMESTAMP
WHERE module_id = 101 AND status = 'RETRYING';
```

**알림 메시지**
```
[ALERT_BAR] Info: 프로젝트 A 알림 재전송 성공
[Slack] [Info] 프로젝트 A 실행이 자동 재시작되었습니다.
[Telegram] Info: 프로젝트 A 실행 자동 재시작 성공
[Email] Subject: Info - 프로젝트 A 알림 재전송 성공
```

---

## 📌 전체 흐름 요약
1. **PENDING** → 알림 최초 기록  
2. **FAILED** → 외부 알림 전송 실패, DB에 실패 상태 기록  
3. **RETRYING** → 재시도 프로세스 실행  
4. **SENT** → 재전송 성공, DB 상태 업데이트 및 알림 정상 반영

# 📊 알림 로그 분석 및 시각화 흐름

알림 로그는 단순한 이벤트 기록을 넘어, **운영 상태 모니터링·장애 추적·재시도 성공률 분석**에 중요한 데이터 자원이 됩니다. 아래는 알림 로그를 **분석 및 시각화**하는 전체 흐름을 단계별로 정리한 시나리오입니다.

---

## 🕒 Step 1. 로그 수집
- **로그 저장**: 모든 알림 이벤트(`alert_logs`)는 DB에 기록  
- 주요 필드: `module_id`, `priority`, `message`, `status(PENDING/FAILED/RETRYING/SENT)`, `created_at`, `updated_at`

---

## 🕒 Step 2. 데이터 정제
- **로그 필터링**: 특정 기간, 모듈, 상태별로 추출  
- **중복 제거**: 동일 알림이 여러 번 기록된 경우 하나로 합산  
- **상태 변환**: FAILED → RETRYING → SENT 흐름을 타임라인으로 정리

---

## 🕒 Step 3. 분석
- **실패율 분석**: 전체 알림 중 FAILED 비율 계산  
- **재시도 성공률**: RETRYING 후 SENT로 전환된 비율  
- **우선순위별 분포**: Info/Warning/Error 알림 비율  
- **모듈별 알림 빈도**: 어떤 모듈에서 알림이 집중되는지 파악

---

## 🕒 Step 4. 시각화
- **시간 시계열 그래프**: 알림 발생 추세 (시간대별)  
- **상태 전환 Sankey 다이어그램**: FAILED → RETRYING → SENT 흐름 시각화  
- **우선순위 파이차트**: Info/Warning/Error 비율  
- **모듈별 바차트**: 모듈별 알림 발생 건수 비교  





---

## 🕒 Step 5. 사용자 통지 및 대시보드 반영
- 관리자 페이지에서 **실시간 알림 대시보드** 제공  
- 외부 알림 시스템(Slack/Telegram/Email)에도 **분석 요약 리포트** 전송 가능  

---

## 📌 요약
1. **로그 수집** → DB에 알림 이벤트 기록  
2. **데이터 정제** → 기간·모듈·상태별 필터링  
3. **분석** → 실패율, 재시도 성공률, 우선순위 분포, 모듈별 빈도  
4. **시각화** → 시계열 그래프, Sankey 다이어그램, 파이차트, 바차트  
5. **사용자 통지** → 관리자 대시보드 + 외부 알림 시스템 리포트

# 📊 알림 로그 분석 및 시각화 – SQL 쿼리 병합 시나리오

아래는 **알림 로그(`alert_logs`)를 추출·집계·시각화용 데이터셋으로 변환**하는 과정을 실제 SQL 쿼리 예시와 함께 정리한 흐름입니다.

---

## 🕒 Step 1. 로그 추출 (Raw Data)
```sql
SELECT module_id, priority, message, status, created_at, updated_at
FROM alert_logs
WHERE created_at BETWEEN '2026-07-01' AND '2026-07-27';
```
- 특정 기간 동안 발생한 알림 로그를 가져옴  
- **로그 필터링** 단계  

---

## 🕒 Step 2. 상태별 집계
```sql
SELECT status, COUNT(*) AS count
FROM alert_logs
GROUP BY status;
```
- 알림 상태별(PENDING, FAILED, RETRYING, SENT) 건수 집계  
- **실패율 분석**, **재시도 성공률** 계산에 활용  

---

## 🕒 Step 3. 우선순위별 분포
```sql
SELECT priority, COUNT(*) AS count
FROM alert_logs
GROUP BY priority;
```
- Info / Warning / Error 알림 비율 확인  
- **우선순위 파이차트** 시각화에 활용  

---

## 🕒 Step 4. 모듈별 알림 빈도
```sql
SELECT module_id, COUNT(*) AS alert_count
FROM alert_logs
GROUP BY module_id
ORDER BY alert_count DESC;
```
- 어떤 모듈에서 알림이 집중되는지 파악  
- **모듈별 알림 바차트** 시각화에 활용  

---

## 🕒 Step 5. 상태 전환 타임라인
```sql
SELECT module_id, message, status, created_at
FROM alert_logs
WHERE module_id = 101
ORDER BY created_at ASC;
```
- 특정 모듈의 알림 상태 변화를 시간 순으로 추적  
- **상태 전환 Sankey 다이어그램** 시각화에 활용  

---

## 📌 시각화 예시
- **시간 시계열 그래프** → 알림 발생 추세  
- **Sankey 다이어그램** → FAILED → RETRYING → SENT 흐름  
- **파이차트** → 우선순위별 비율  
- **바차트** → 모듈별 알림 발생 건수

# 🚦 알림 우선순위 정책 적용 흐름

알림 로그가 단순히 기록되는 것에서 나아가, **우선순위 정책**을 적용하면 운영자가 알림을 더 효과적으로 관리할 수 있습니다. 아래는 **Info / Warning / Error** 우선순위 정책이 실제로 적용되는 흐름을 단계별로 정리한 시나리오입니다.

---

## 🕒 Step 1. 알림 발생
- 모듈 실행 엔진에서 이벤트 발생 → 알림 로그 생성  
- 알림 로그에 `priority` 필드 포함 (Info, Warning, Error)

```sql
INSERT INTO alert_logs (module_id, priority, message, status, created_at)
VALUES (101, 'Warning', '프로젝트 A 실행이 타임아웃으로 종료되었습니다.', 'PENDING', CURRENT_TIMESTAMP);
```

---

## 🕒 Step 2. 정책 매핑
- **Info 알림** → 관리자 페이지 알림 바에만 표시  
- **Warning 알림** → 관리자 페이지 + 외부 알림 시스템 전송  
- **Error 알림** → 관리자 페이지 + 외부 알림 시스템 + SMS/전화 등 긴급 채널 전송  

---

## 🕒 Step 3. 알림 브로커 처리
- 알림 브로커(Alert Dispatcher)가 DB의 `alert_logs`를 읽음  
- 우선순위 정책에 따라 전송 채널 결정  

```
[ALERT_DISPATCHER] Warning 알림 → Slack/Telegram 전송
[ALERT_DISPATCHER] Error 알림 → Slack/Telegram + SMS 전송
```

---

## 🕒 Step 4. 외부 알림 시스템 연동
- Slack, Telegram, Email, SMS 등으로 알림 전송  
- 우선순위별로 채널 다르게 적용  

```
[Slack] [Warning] 프로젝트 A 실행이 타임아웃으로 종료되었습니다.
[Telegram] Warning: 프로젝트 A 실행 자동 종료
[SMS] [Error] 프로젝트 B 실행 실패 – 즉시 확인 필요
```

---

## 🕒 Step 5. 사용자 확인
- 관리자 페이지 알림 바에서 모든 알림 확인 가능  
- 외부 알림 시스템에서는 우선순위 정책에 따라 알림 수신  

```
[ALERT_BAR] Info: 프로젝트 A 자동 재시작 성공
[ALERT_BAR] Warning: 프로젝트 A 실행 타임아웃 종료
[ALERT_BAR] Error: 프로젝트 B 실행 실패 – 긴급 조치 필요
```

---

## 📌 요약
1. **알림 발생** → 로그 기록 (priority 포함)  
2. **정책 매핑** → Info/Warning/Error 별 전송 채널 결정  
3. **알림 브로커 처리** → DB 로그 읽고 정책 적용  
4. **외부 시스템 연동** → Slack/Telegram/Email/SMS 전송  
5. **사용자 확인** → 관리자 페이지 + 외부 알림 시스템에서 확인  

---

# 📑 우선순위 정책 흐름 – 시퀀스 다이어그램 (텍스트 버전)

아래는 **DB → 알림 브로커 → 외부 시스템 → 사용자**까지의 메시지 교환을, **우선순위 정책(Info / Warning / Error)** 적용 흐름으로 정리한 시퀀스 다이어그램 텍스트 버전입니다.

---

```
모듈 실행 엔진        DB 계층                  알림 브로커              외부 알림 시스템(Slack/Telegram/Email/SMS)        사용자
     │                   │                        │                                  │                                  │
     │--- 이벤트 발생 --->│                        │                                  │                                  │
     │                   │--- system_logs 기록 --->│                                  │                                  │
     │                   │--- alert_logs 기록 ---->│                                  │                                  │
     │                   │                        │--- 알림 로그 읽기 ---------------->│                                  │
     │                   │                        │--- 우선순위 정책 적용 ------------>│                                  │
     │                   │                        │                                  │--- Info 알림 → 관리자 페이지 ---->│
     │                   │                        │                                  │--- Warning 알림 → Slack/Telegram->│
     │                   │                        │                                  │--- Error 알림 → Slack/Telegram + SMS/Email
     │                   │                        │<-- 전송 결과 반영 ----------------│                                  │
     │                   │--- alert_logs 업데이트 (SENT/FAILED) ---------------------->│                                  │
     │                   │                        │                                  │                                  │--- 알림 확인
     │                   │                        │                                  │                                  │<-- 알림 메시지 수신
```

---

## 📌 단계별 설명
1. **모듈 실행 엔진** → 이벤트 발생 후 DB에 로그 기록 (`system_logs`, `alert_logs`).  
2. **알림 브로커** → DB에서 알림 로그 읽고 우선순위 정책 적용.  
   - Info → 관리자 페이지 알림 바만 표시  
   - Warning → 관리자 페이지 + Slack/Telegram  
   - Error → 관리자 페이지 + Slack/Telegram + SMS/Email  
3. **외부 알림 시스템** → 정책에 따라 알림 전송.  
4. **DB 계층** → 전송 결과 반영 (`SENT` 또는 `FAILED`).  
5. **사용자 확인** → 관리자 페이지 + 외부 알림 시스템에서 알림 메시지 확인.  

---


  ```
  [ALERT_BAR] Warning: 프로젝트 A 실행 타임아웃 종료
  [Slack] [Warning] 프로젝트 A 실행이 타임아웃으로 종료되었습니다.

  ```

# 🚦 알림 정책 최적화 전략

알림 시스템은 단순히 이벤트를 전달하는 것에 그치지 않고, **정확성·효율성·사용자 경험**을 높이기 위해 정책을 최적화할 필요가 있습니다. 아래는 **실패·재시도·성공 흐름**과 **우선순위 정책**을 기반으로 한 최적화 전략입니다.

---

## 1️⃣ **우선순위 기반 채널 최적화**
- **Info** → 관리자 페이지 알림 바에만 표시 (불필요한 외부 알림 최소화)  
- **Warning** → Slack/Telegram 등 협업 채널로 전송  
- **Error** → Slack/Telegram + SMS/Email 등 긴급 채널까지 확장  
- **효과**: 알림 과잉을 줄이고, 중요한 알림은 빠르게 전달  

---

## 2️⃣ **실패율 관리 및 재시도 정책**
- 전송 실패 시 **재시도 횟수 제한** (예: 3회)  
- 실패 로그는 반드시 DB에 기록 → 장애 원인 분석 가능  
- 재시도 성공률을 KPI로 관리 → 정책 개선 지표로 활용  

---

## 3️⃣ **알림 집계 및 배치 전송**
- 동일 모듈에서 짧은 시간 내 다수 알림 발생 시 **배치 처리**  
- 예: “프로젝트 A에서 5건의 Warning 발생” → 하나의 알림으로 요약  
- **효과**: 사용자 피로도 감소, 알림 효율성 증가  

---

## 4️⃣ **사용자 맞춤형 정책**
- 관리자별로 알림 채널/우선순위 설정 가능  
- 예: 운영팀 → Error 알림만 SMS, 개발팀 → Warning 알림 Slack  
- **효과**: 역할 기반 최적화, 불필요한 알림 최소화  

---

## 5️⃣ **대시보드 KPI 관리**
- **실패율**: 전체 알림 중 FAILED 비율  
- **재시도 성공률**: RETRYING → SENT 전환 비율  
- **우선순위 분포**: Info/Warning/Error 비율  
- **모듈별 집중도**: 특정 모듈에서 알림 집중 여부  

---

## 📌 요약
- **우선순위 정책 최적화** → 알림 채널 효율화  
- **재시도 정책 강화** → 실패율 관리 및 안정성 확보  
- **집계·배치 전송** → 알림 과잉 방지  
- **사용자 맞춤형 정책** → 역할 기반 최적화  
- **대시보드 KPI 관리** → 운영 지표 기반 개선

# 📑 알림 정책 최적화 전략 – 시퀀스 다이어그램 (텍스트 버전)

아래는 **DB → 알림 브로커 → 외부 시스템 → 사용자**까지의 흐름을, **알림 정책 최적화 전략**을 반영해 정리한 시퀀스 다이어그램 텍스트 버전입니다.  
(우선순위 정책 + 실패·재시도·성공 관리 + 집계·배치 전송 + 사용자 맞춤형 정책 포함)

---

```
모듈 실행 엔진        DB 계층                  알림 브로커              외부 알림 시스템(Slack/Telegram/Email/SMS)        사용자
     │                   │                        │                                  │                                  │
     │--- 이벤트 발생 --->│                        │                                  │                                  │
     │                   │--- system_logs 기록 --->│                                  │                                  │
     │                   │--- alert_logs 기록 ---->│                                  │                                  │
     │                   │                        │--- 알림 로그 읽기 ---------------->│                                  │
     │                   │                        │--- 우선순위 정책 적용 ------------>│                                  │
     │                   │                        │--- 집계/배치 전송 정책 적용 ------>│                                  │
     │                   │                        │--- 사용자 맞춤형 정책 적용 -------->│                                  │
     │                   │                        │                                  │--- Info 알림 → 관리자 페이지 ---->│
     │                   │                        │                                  │--- Warning 알림 → Slack/Telegram->│
     │                   │                        │                                  │--- Error 알림 → Slack/Telegram + SMS/Email
     │                   │                        │                                  │--- 전송 실패 --------------------->│
     │                   │                        │<-- 실패 상태 반영 ----------------│                                  │
     │                   │--- alert_logs 업데이트 (FAILED) --------------------------->│                                  │
     │                   │                        │--- 재시도 큐 등록 ---------------->│                                  │
     │                   │                        │--- 재시도 실행 ------------------->│                                  │
     │                   │                        │                                  │--- 알림 재전송 ------------------>│
     │                   │                        │                                  │--- 전송 성공 -------------------->│
     │                   │                        │<-- 성공 상태 반영 ----------------│                                  │
     │                   │--- alert_logs 업데이트 (SENT) ----------------------------->│                                  │
     │                   │                        │                                  │                                  │--- 알림 확인
     │                   │                        │                                  │                                  │<-- 알림 메시지 수신
```

## 📌 최적화 전략 반영 포인트

- **실패·재시도 정책** → 실패 시 DB 기록, 재시도 큐 등록, 성공률 KPI 관리

# 📑 관리자 페이지 – 플러그인 및 모듈 서비스 관리 시퀀스 다이어그램 (텍스트 버전)

구글 클라우드 콘솔처럼 좌측 메뉴가 있는 관리자 화면을 기준으로, **플러그인 및 모듈 서비스 관리 대시보드**의 흐름을 시퀀스 다이어그램 텍스트 버전으로 정리했습니다.

---

```
관리자(사용자)          좌측 메뉴(Navigation)       대시보드 컨트롤러          DB 계층                  알림 브로커            외부 알림 시스템
     │                          │                          │                        │                        │                        │
     │--- 메뉴 클릭 ------------>│                          │                        │                        │                        │
     │                          │--- 요청 전달 ------------>│                        │                        │                        │
     │                          │                          │--- 모듈/플러그인 상태 조회 -->│                        │                        │
     │                          │                          │                          │--- SELECT * FROM plugins/modules
     │                          │                          │<-- 상태 데이터 반환 ------│                        │                        │
     │                          │                          │--- 알림 로그 조회 -------->│                        │                        │
     │                          │                          │                          │--- SELECT * FROM alert_logs
     │                          │                          │<-- 알림 로그 반환 --------│                        │                        │
     │                          │                          │--- 정책 적용 ------------>│                        │                        │
     │                          │                          │                          │--- 우선순위/집계/재시도 정책 반영
     │                          │                          │--- 알림 브로커 호출 ------>│                        │--- 알림 전송 ---------->│
     │                          │                          │                          │                        │--- Info → 관리자 페이지
     │                          │                          │                          │                        │--- Warning → Slack/Telegram
     │                          │                          │                          │                        │--- Error → Slack/Telegram + SMS
     │                          │                          │<-- 전송 결과 반영 --------│                        │<-- 상태 업데이트 -------│
     │<-- 대시보드 화면 갱신 ----│<-------------------------│                        │                        │                        │
```

---

## 📌 흐름 설명
1. **관리자**가 좌측 메뉴에서 "플러그인 관리" 또는 "모듈 서비스 관리" 클릭  
2. **대시보드 컨트롤러**가 DB에서 플러그인/모듈 상태와 알림 로그 조회  
3. **알림 브로커**가 정책(우선순위, 집계, 재시도)을 적용해 외부 알림 시스템으로 전송  
4. **외부 알림 시스템**은 Info/Warning/Error에 따라 채널별로 알림 전달  
5. **DB**는 전송 결과를 업데이트 (SENT/FAILED/RETRYING)  
6. **대시보드 화면**은 KPI 카드, 그래프, 로그 테이블로 갱신되어 관리자에게 표시  

---

## 📊 대시보드 반영 요소
- **상단 KPI 카드** → 실패율, 재시도 성공률, 모듈 집중도  
- **중앙 패널** → Sankey 다이어그램 (FAILED → RETRYING → SENT)  
- **좌측 패널** → 플러그인 상태 목록 (버전/업데이트 여부)  
- **우측 패널** → 모듈 서비스 상태 (실행/중지/에러)  
- **하단 패널** → 알림 로그 테이블 (검색/필터링 지원)
