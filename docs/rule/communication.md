---

## 1. 기본 원칙
- 감성적 미사여구(프리미엄, 굉장한, 와우 등) 사용 금지.
- 작업 결과는 구체적인 코드 변경점, 수치, 파일 경로를 통해 사실 위주로 보고.
- 근거 없는 추측성 설명 대신 코드/로그/데이터에 기반한 설명을 우선한다.

## 2. 전문 용어의 명확성
- 디자인 설명 시 미학적 표현 대신 HEX 코드, px 단위, 레이아웃 구조(Flex, Grid 등)를 사용한다.
- 기술적 결정 시 라이브러리 명칭, 알고리즘 특징, 성능상의 이점을 명시한다.

## 3. 응답 구조
1. **작업 요약**: 수행한 작업을 한 줄로 요약
2. **기술적 변경 내역**: 변경된 파일, 함수, 로직에 대한 사실 나열
3. **변경 이유**: 무엇을 개선하거나 해결하려 했는지 근거를 함께 기록한다. 이유를 남기지 않으면 이후 동일한 문제에 같은 제안이 반복될 수 있다.
4. **검증 방법**: 변경사항이 의도대로 동작하는지 확인한 방법(테스트 실행, 로그 확인 등)을 기록한다.
5. **확인 사항**: 사용자가 즉시 확인해야 할 기술적 포인트나 실행 명령
6. **다음 작업(해당하는 경우)**: 이어서 진행이 필요한 항목
7. **이력 관리**: `docs/todo.history.md` 및 `docs/askLogs/` 업데이트 내역 고지, 필요 시 ADR(`workflow-management.md` 5장) 작성 여부 고지

## 4. 금지 표현
- "프리미엄한", "놀라운 첫인상", "당신을 놀라게 할" 등 마케팅성 문구
- "최고 품질의", "완벽한" 등 주관적·단정적 수식어
